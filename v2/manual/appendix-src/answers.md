# Answers collected for the appendix of volume 2 (Chinese, concise)

## 第 1 章
1. `system-reserved cpu = 16 − 2 = 14`，allocatable CPU = 16 − 14 − 0.25 = 1.75。驱逐从用量达到 4096 − 150 = 3946 MiB 开始，所以 `eviction-hard memory.available < 15642 − 3946 = 11696Mi`；allocatable 内存 = 15642 − 256 − 11696 = 3690 MiB。节点容器相应地改为 `docker update --cpuset-cpus <一个物理核心的两个线程> --memory 4096m --memory-swap 4096m`。
2. 实际用量 2.8 GiB（2867 MiB）尚未达到驱逐起点 2922 MiB（信号为 15642 − 2867 = 12775 MiB，高于阈值 12720 MiB），kubelet 什么也不做；requests 之和 2.5 GiB 也没有超过 allocatable 2666 MiB，调度器仍可能放入新 Pod。再分配 400 MiB 后用量将超过 3072 MiB 的内核上限。kubelet 默认每 10 秒才检查一次驱逐信号，3 秒内来不及反应，最可能的结果是内核 OOM：在节点 cgroup 内按 `oom_score` 挑选进程，BestEffort（1000）最先，其次是超出 requests 最多的 Burstable，容器以 137 退出（`OOMKilled`）并原地重启。只有当用量在 2922–3072 MiB 之间停留到 kubelet 的下一次检查时，才会发生有序驱逐。结论：驱逐余量必须大于“一个检查周期内可能增长的内存”。
3. 先 `kubectl get --raw /api/v1/nodes/<节点>/proxy/configz | jq .kubeletconfig.evictionHard`，只看到三个磁盘信号。在 Kind 配置中加入 `kubeadmConfigPatches: ["kind: KubeletConfiguration\nevictionHard:\n  memory.available: \"500Mi\"\n  nodefs.available: \"0%\"\n  nodefs.inodesFree: \"0%\"\n  imagefs.available: \"0%\""]`，重建集群后再查一次。保留三个 `0%` 是为了明确地关闭磁盘驱逐：节点容器看到的是整个主机的磁盘，若将来 `mergeDefaultEvictionSettings` 被设为 true 或默认行为改变，没写的信号会套用默认值（如 `nodefs.available<10%`、`imagefs.available<15%`），主机磁盘被别的东西占满时，所有节点都会开始驱逐 Pod、回收镜像，而原因与节点本身无关。
4. 配额（`--cpus 4`）下进程仍能看到 16 个 CPU。Go 1.25 之前的程序会按 16 启动 P（GOMAXPROCS），16 个线程并行时 25 ms 就用完 100 ms 周期内的 400 ms 配额，随后被暂停 75 ms，表现为周期性的延迟尖峰，可观测节点 cgroup 的 `cpu.stat` 中 `nr_throttled`、`throttled_usec` 增长；cpuset 下 GOMAXPROCS 为 4，不会被节流。Python 多进程程序若按 `os.process_cpu_count()` 启动工作进程，cpuset 下是 4 个，配额下是 16 个，内存占用翻几倍，进程之间争抢 4 个 CPU 的配额，可观测进程数、RSS 与 `nr_throttled`。CPU 密集型 Pod 在 cpuset 下只在 CPU 4-7 上竞争，饱和时表现为调度延迟（`cpu.pressure` 的 some 值上升）；配额下它可以跑在全部 16 个线程上，与其他节点的进程共享物理核心（SMT 兄弟线程、缓存），形成跨节点的吵闹邻居，节点总用量超过 4 个 CPU 时整个节点被节流。
5. ① 负载均衡器本身：`kubectl get svc` 看 EXTERNAL-IP 是否已分配，`docker ps --filter label=io.x-k8s.cloud-provider-kind.cluster=ent` 看 envoy 容器是否在运行，`docker logs <envoy 容器>` 看健康检查事件（`add_healthy_event`）和访问日志中的响应标志（`UH` 表示没有健康的后端）。② 健康检查的目标：envoy 的集群配置（`/home/envoy/cds.yaml`）中的检查间隔与阈值，以及每个节点上 `curl http://<节点 IP>:10256/healthz`（kube-proxy 的健康端点）是否返回 200。③ 服务端点与转发规则：`kubectl get endpointslices -l kubernetes.io/service-name=<服务>` 看就绪的端点数，Pod 的就绪探针是否通过，`docker exec <节点> iptables-save | grep <服务>` 看 KUBE-SVC/KUBE-SEP 链及其概率，kube-proxy 日志中规则同步的时间。
6. 审计日志在 Metadata 级别已经记录了“谁、何时、对哪个 Secret、做了什么操作”，缺的只是“值是否被篡改”。做法：① 让人不直接写 Secret，由外部密钥管理系统（Vault/OpenBao、云的 Secrets Manager）保存值和版本历史，并由 External Secrets 之类的控制器同步到集群；密钥系统自己的审计日志记录谁改了值，集群审计日志中写 Secret 的只应是同步控制器，出现其他写入者即为异常。② 需要在集群侧比对时，记录值的指纹而不是值本身：用只有审计系统持有的密钥计算 HMAC（不要用普通哈希，短密码的 SHA-256 可以被穷举），由准入控制器或同步控制器写进注解或外部的防篡改日志，定期与密钥系统中的版本比对。③ 配合 etcd 静态加密，防止绕过 API 直接读取存储。
