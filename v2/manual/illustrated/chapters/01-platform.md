# 平台基线：谁决定一个节点有多大 {#ch1}

<p class="subtitle">Platform Baseline · 资源边界与故障域</p>

一台电脑可以显示“三个工作节点、三个可用区”，但它仍只有一块磁盘和一个电源。若调度器以为每个节点都有整台虚拟机的内存，它会把一个看似宽裕的集群调度到 OOM。本章先建立资源的空间模型，再用同一个节点的三条内存线解释调度、驱逐和内核限制为什么会给出不同答案。

::: mission
学完后应能从宿主机一直画到 Pod，算出节点的可分配内存，并判断一次 Pending、Evicted 或 OOMKilled 分别应找谁。
:::

## 从 Windows 到 Pod：上限会向内传递

Kind 的“节点”是 Docker 容器，里面运行 kubelet、containerd 和 systemd；Pod 的容器又由内部的 containerd 创建。Docker Engine 运行在 WSL2 虚拟机中，Windows 再约束这台虚拟机。它们不是五份独立的物理资源。

{{fig:concept-env-nesting.svg}}

按图从外向内看：虚拟机的总额限制整个 Linux 环境；节点容器的 cgroup 限制节点组件及其全部 Pod；Pod 容器的 limits 再约束业务进程。子 cgroup 的用量记入父级。因此，一个 Pod 即使自己的内存限制尚未到达，也可能因为节点父 cgroup 耗尽而受影响。

实验宿主机有 8 个物理核心、16 个硬件线程，WSL 的 MemTotal 约为 15642 MiB。E0 将每个工作节点固定到 4 个逻辑 CPU，并把内存硬上限设为 3072 MiB。四个逻辑 CPU 在此对应两个完整物理核心；不能把“4 CPU”再解释为四个独占物理核心。控制面、GitLab、宿主机任务仍会争用其他共享资源。[E0](#ev-e0)

cpuset 与 CPU 配额解决不同问题。cpuset 限制任务可以在哪些处理器上运行；配额限制一段时间内能消耗多少 CPU 时间。即使平均 CPU 没到限制，突发工作仍可能提前用完周期配额，等下一个周期才能继续。第 5 章将看到这段暂停怎样变成事件循环延迟。

## 三个角色，三种资源真相

调度器问的是“承诺出去的 requests 还放得下吗”；kubelet 问的是“当前压力是否需要驱逐”；内核问的是“硬限制是否已经耗尽”。调度器没有通过实际内存用量来替代 requests 的加法。requests 很小、真实用量很大，会让账面仍可调度而实际空间已经危险。

{{fig:concept-kubelet-capacity.svg}}

本实验的 kubelet 容量来自容器没有隔离的宿主视图：节点实际上只有 3 GiB，上报的 memory capacity 却约为 15.28 GiB。仅给 Docker 加 `memory.max` 并不能让调度器知道这个边界；仅减少 allocatable 也不能保证驱逐信号及时到达阈值。要同时校正记账和压力判断。

内存的关系可写成：

$$A=C-K-S-E$$

这里 $C$ 是上报 capacity，$K$、$S$ 是 kube 与 system 预留，$E$ 是用于 allocatable 计算的硬驱逐预留。压力信号另按 $memory.available=C-workingSet$ 计算。workingSet 扣除了可回收的非活跃文件页，不能直接等同于 RSS。

::: case
**例：给 3 GiB 节点留出 150 MiB 的驱逐反应空间。**希望实际工作集到 $3072-150=2922$ MiB 时触发，阈值应为 $15642-2922=12720$ MiB。再给节点组件留 256 MiB，得到 $A=15642-12720-256=2666$ MiB。

这个“大得反常”的阈值包含了不属于节点的幻影容量。它是 Kind 嵌套环境的换算，不能抄到容量真实的生产节点上。
:::

{{fig:e0-memory-lines.svg}}

图中的三条线使用不同的量：2666 MiB 是 requests 的调度边界，2922 MiB 是节点工作集的驱逐起点，3072 MiB 是父 cgroup 的硬限制。它们之间的空间负责吸收节点进程开销与驱逐采样延迟，并不意味着任何单个 Pod 都获得这份余量。

## 容量预算必须把平台也算进去

暂停第一册集群后，WSL 仍有 GitLab、镜像缓存、Docker 与内核的固定成本。E0 空集群创建 60 秒后的控制面约 699 MiB，工作节点约 139–199 MiB；GitLab 约 3 GiB。三个工作节点的 9 GiB 预算不是虚拟机可以全部交给业务的空闲内存。

这里有两个经常混淆的计划。**装箱计划**按 requests 检查每个节点能否接纳 Pod；**运行计划**按工作集、峰值、页缓存与父 cgroup 上限检查是否安全。还要为滚动更新时的新旧副本共存、节点失效后的替代者保留空间。第 7 章的真实事故正是装箱接近 99% 时，一次正常发布让监控先被驱逐。

第 8 章加入备份组件时，工作节点历史上从 3 GiB 扩到 3.5 GiB，可分配内存从 2666 增到 3178 MiB。读后半书时不能继续拿 E0 的节点尺寸计算所有实验；这次扩容有记录，本版没有再次改变环境。

## 三个可用区标签能教什么

`topology.kubernetes.io/zone` 给调度器一个故障域名称。它能检验副本分布约束如何作用，能通过冻结节点或丢包观察控制器如何反应。它没有创造独立电源、内核、磁盘或网络设备。主机睡眠会让三个“区”、GitLab 和告警桥一起沉默。

::: principle
判断多可用区设计，先找共享故障点，再数标签。副本分散到三个节点，只能降低节点级故障的相关性；共享的宿主机仍是它们共同的边界。
:::

新建 LoadBalancer 的短暂冷启动失败、控制面无内存硬上限等历史风险仍保留于 [E0](#ev-e0)；那次 43 秒建群不能作为任何机器的交付时限。
