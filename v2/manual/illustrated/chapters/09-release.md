# 发布治理：凭什么继续，何时必须撤回 {#ch9}

<p class="subtitle">Release Governance · 一次完整的业务发布判断</p>

一个配置改动通过 CI、进入 main，Argo CD 自动同步。几分钟后订单失败：合并前的门禁负责什么，金丝雀观察负责什么，谁有权撤回？本章沿一次真实历史发布读完整条路径，并把自动合规检查与尚未自动化的业务判断分开。

::: mission
能解释 GitOps 下合并为何是发布决定，计算金丝雀影响面与观察量，理解冻结和部署身份，并正确解读本项目 DORA 数据的统计口径。
:::

## GitOps 把发布决定前移到合并

Argo CD 持续把受管理对象拉向 Git 声明；main 出现什么清单，正常情况下就会进入集群。因此检查若只在集群准入才发生，错误已经进入正式期望状态，Argo CD 会继续失败与重试。

{{fig:concept-release-path.svg}}

沿图分清三种工作：流水线先渲染和检查，Maintainer 决定接受变更，Argo CD 执行收敛，应用指标再检验业务。配置合法不是业务健康，Synced 也不是订单成功。

{{code:release-gate}}

这段真实流水线先保存 Helm 渲染结果，再对生产与租户运行 Kyverno 发布策略。它与 Argo CD 采用相同的输入组合，减少“检查了一份、部署另一份”。项目设置还要求流水线成功才能合并，main 拒绝直接推送；单写一个 CI 作业而允许绕过，不构成门禁。

E8 违规镜像、内存限制和副本数在 31–48 秒内被拒，合并返回 405；合规修改合并后 27 秒滚动完成。它验证了被覆盖的配置规则；平台自身与流程外升级当时不完全覆盖，后续才逐步接管。[E8](#ev-e8)

## 案例：把新网关放到 5% 公共请求上

历史金丝雀使用第二个 Helm release `gateway-canary`，同一 Chart、不同镜像。HTTPRoute 先匹配 `x-storefront-preview: canary`，其余公共请求按 95/5 权重。零公共权重时，团队仍可通过预览头验证新版本。

{{fig:concept-canary-routes.svg}}

这是历史实验的路由设计。当前源码已提升并清理金丝雀，只保留稳定版 backend；不能为了让示例好看，声称当前 main 仍运行两个版本。完整历史路由与变更见 E8 证据，当前文件的注释也说明了这一演进。

一个完整决定依次问：制品与配置是否允许部署；预览是否满足关键业务；公共样本是否足够；相同时间的稳定版是否健康；用户 SLI 是否退化；撤回路径是否仍可用。前两项通过只能允许进入观察，不能直接允许百分之百提升。

## 在真实发布看板中分清份额和失败

{{shot:canary-share}}

先读图中的 canary share，确认时间区间和分母；约 01:23 的 100% 尖峰来自只带预览头的测试，不是公共路由突然全量。再看故障阶段新版 5xx 与稳定版，区分版本退化和全系统故障。就绪副本始终为 2，并没有阻止业务错误。

E8 公共样本 20001 个中，新版回答 986，约 4.93%；同窗口 Prometheus 约 5.03%。注入新版一半失败时，3596 个公共请求中失败 88，约 2.45%，全部来自金丝雀。相同窗口的客户端计数与服务端计数互相校验，避免仅凭一条曲线下结论。

::: case
**爆炸半径估算。**若请求随机分配、新版失败率 50%、权重 5%，则公共错误约为 $0.05\times0.5=2.5\%$。这已经高于浏览 0.5% 的错误预算比例，需要尽快撤回。

若入口 100 请求/秒、观察 90 秒，新版期望只得到约 450 个样本。若只失败 1 次，不能凭这个样本精确断言生产错误率；最低请求数、窗口长度、置信度和业务分层都应写进自动分析设计。总流量很低时，固定等待一分钟可能什么也没有检验。
:::

## Abort 与 Promotion 都是可追踪变更

E8 故障注入约 90 秒后脚本做撤回决定，经门禁 43 秒合并，决定后 46.1 秒最后一次由金丝雀回答。恢复后的一段观察没有失败；后续提升期间 8697 个请求零失败。这里零失败只描述该次样本，不能证明新版本永远没有缺陷。

{{fig:e8-canary.svg}}

原工程没有实现自动指标分析、自动 promotion 或自动 abort；决定由演练脚本按时间做出。发布门禁是自动的合规检查，金丝雀业务判定尚需人或新控制器。新版提供判断方法，不把设计建议写成现有能力。

撤回应改变 Git 中的期望，使 Git 与运行状态重新一致。若只在集群手工改权重，下一次自愈可能重新放量。紧急时也要保留变更理由、操作者、开始影响和结束影响的时间，方便事故与 DORA 关联。

## 冻结需要挡住合并与同步两个位置

{{fig:concept-freeze-keys.svg}}

GitLab 冻结期检查拒绝普通合并请求，带 `[emergency]` 的请求仍接受其他门禁；Argo CD deny 窗口阻止已合并变更自动同步，允许有记录的手动操作。只有第一层会漏掉流程外进入 main 的变更，只有第二层会积累待发布改动、在窗口结束一起涌出。

原实验中紧急改动通过门禁，deny 窗口仍挡住它；手动同步放行 catalog，orders 到窗口结束后约 76 秒才自动同步。这个“紧急”是模拟情节，连接池没有真的耗尽。提交消息中的标记也不能独自充当生产审批制度，真实流程还需权限与记录相互约束。

## 发布身份与空集群依赖

sync impersonation 让 Argo CD 用项目部署账号写 Kubernetes：团队账号无权直接读写 Secret，API Server 可以真正拒绝。根应用也需要专属 root 项目和账号，否则它会因无匹配身份失去自我修复能力。历史启用曾造成约 7 分钟根应用无法同步；平台账号仍是 cluster-admin，隔离只覆盖设定的项目边界。

波次是依赖图的执行方式，不能只根据“看起来更快”重排。R3 把 HTTPRoute 放在 Service 之前，路由 BackendNotFound 使 mesh Degraded，根应用等待它健康，后面的 Service 永远不能出现。另一次 Kyverno 生成规则与 Git 争同一对象，原先只写在注释中的先后假设被并行化打破。

修复后 R4 从根同步起 636 秒全部就绪，相比 R2 的 692 秒快 56 秒；CRD 与恢复耗时本身却波动约一两分钟。结构上少了关键路径等待是可解释的，单次总时间不足以证明固定百分比加速。重建检验的是依赖，不是给排版中的波次图凑一组漂亮数字。

## DORA 数字首先需要清楚的分母

项目脚本把合并请求修改的文件映射到应用输入，再匹配包含提交的第一次部署。历史 5.5 小时记录中有 16 个 MR、56 次应用部署，中位前置约 1.2 分钟，按 MR 的失败约 1/16；六个业务服务又是另一范围。不能把每个应用同步都当作一个团队独立发布，也不能把数小时折算的“每日频率”当长期表现。

“恢复 7 分钟”按部署到部署计算，包含金丝雀健康运行的时间；从真正注入故障到恢复约 138 秒。流程外的 helm 修改导致根应用故障，没有进入 MR 记录，也就没有被脚本计入失败。DORA 度量依赖事件完整性，追踪缺失比小数位更值得关注。

## 判断与应用

::: exercise
1. 金丝雀权重 5%、自身失败率 40%，入口 100 请求/秒，3 分钟后撤回。估算坏请求数；若月流量稳定为同样速率、SLO99.5%，算预算消耗比例。
2. 设计一份允许自动提升或撤回的分析规则：至少列出业务 SLI、稳定版对照、最少样本、观察窗口、缺数据处理和执行失败处理。指出哪些超出当前实现。
3. 一个路由依赖后续波次创建的 Service，根应用又等待路由 Healthy。画出等待环，提出一种消除环的划分方式。
:::

允许继续需要合规、足够样本与业务健康共同支持；必须撤回则要有能执行、能追溯、能验证影响结束的路径。
