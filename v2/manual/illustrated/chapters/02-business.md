# 多服务架构：一笔订单怎样跨过失败 {#ch2}

<p class="subtitle">Multi-Service Architecture · 从业务状态读懂真实代码</p>

顾客已经付钱，订单却显示失败。这不是“重试次数不够”就能修复的问题：扣款和订单由两个服务保存，网络超时没有告诉我们对方是否已提交。本章从正常下单出发，逐步拆开唯一键、库存事务、补偿和事件投递，最后回到真实发生过的模糊结果。

::: mission
目标是能沿源码推演一次成功、重复请求和支付结果未知的订单，并准确指出每一层原子性在哪里结束。后续容量、弹性、韧性与可观测性章节都使用这条链路。
:::

## 六个服务，各自拥有什么状态

gateway 是面向客户端的入口，catalog 提供价格，orders 编排订单，inventory 管理可售与预留库存，payments 模拟外部支付商，notifier 消费已确认事件并模拟通知。它们共用一个镜像，但运行在独立 Deployment 中。共享构建不等于共享进程，也不等于必须一起发布。

{{fig:concept-storefront.svg}}

先沿图中的同步路径走：客户端把商品和数量交给 gateway，gateway 把幂等键原样转发给 orders；orders 并行查价，然后依次预留、支付、确认。价格查询可以并行，因为两者没有顺序依赖；支付必须等库存结果，因为没有货时不应继续扣款。确认后的通知不参与当前响应，转到异步路径。

数据库按服务分库、分角色，但共享一个 PostgreSQL 集群；Valkey 同时承担缓存、支付结果记录和通知去重，NATS JetStream 保存事件。共享基础设施降低实验成本，也留下共同故障域：catalog 的缓存可以丢，支付幂等记录的丢失却可能改变业务结果。把它们放在一个 Valkey 不会消除这种重要性差异。

## 首先占住“这是同一笔订单”的身份

网络请求至少有三种结果：明确成功、明确失败、结果未知。只要客户端可能因未知而重试，就要先给业务操作一个稳定身份。客户端生成 `Idempotency-Key`，不是每次尝试重新生成。

{{code:order-claim}}

`INSERT` 把订单先写成 PENDING。数据库唯一约束负责仲裁同时到来的重复键，`UniqueViolationError` 让失败的一方知道已经有人占住这个业务操作。检查后再插入会留下并发窗口；唯一约束把仲裁放在真正拥有状态的数据库中。

{{code:order-replay}}

重复路径查出已有订单，以 200 和 `Idempotent-Replayed: true` 返回。请注意：**已有结果未必是终局状态**。第一次请求仍在处理时，重放可能返回 PENDING。调用方应读取响应中的业务状态，不能把 HTTP 200 自动解释为“付款与确认都完成”。当前实现也没有把幂等键和请求体指纹绑定；同一个键携带另一份商品清单时仍会重放原订单，这是接口契约需要明确的限制。

gateway 的职责很薄：建立请求截止时间，向 orders 转发原幂等键，再保留状态码与少量响应头。它没有替 orders 建立第二份订单状态，这使幂等身份贯穿整条请求路径。

## 库存原子性：先读后写为什么危险

若两个请求都先读到“库存还有 1”，再各减 1，就可能卖出两件。inventory 把条件放进数据库更新语句，并把一组商品和预留记录放在同一个事务中。

{{code:inventory-guard}}

先看 `WHERE ... available >= $2`：判断与扣减在同一条 UPDATE 中执行，`RETURNING` 没有返回行就表示不能预留。再看外层 `c.transaction()`：任何商品不足都会抛出异常，使前面已经更新的商品一起回滚。最后看 `sorted`：各订单按同一种商品顺序取锁，降低多个热点商品交叉锁定造成的死锁风险。

预留以订单 ID 为主键。并发的重复预留可能都开始执行，但只有一份预留记录能够插入；唯一冲突会回滚输掉的事务，再读取已经存在的预留状态。历史集成测试中 30 个并发请求争抢 5 件库存，恰好 5 个成功、25 个返回 409；这是该输入下的运行证据，不是数据库在任何应用逻辑下都不会超卖的保证。[E1](#ev-e1)

释放库存也需要幂等。它先锁住预留行，已经 RELEASED 就直接返回；否则加回库存并更新状态。重复释放不能重复加库存。这与“同一个 HTTP 请求最多执行一次”无关，它允许请求再次执行，但使重复执行不再改变最终状态。

## Saga：补偿撤销业务效果，不撤销时间

订单、库存和支付分别提交自己的本地事务，无法用一个数据库事务包住整个业务。orders 采用编排式 Saga，记录进度，失败时发起补偿。中间状态对其他请求可见，因此 Saga 不具有跨服务事务的隔离性。

{{fig:concept-saga.svg}}

图中向前的实线表示正常步骤，反向路径表示释放预留。补偿是新的业务操作，会消耗时间、也可能再次失败。orders 的 `release()` 捕获调用错误、增加补偿失败计数并记录日志；它没有一个持久的补偿重试队列。因此“代码里写了补偿”并不等于库存一定立刻释放。

{{code:payment-failure}}

402 是支付商明确拒付，可以释放库存并给出 PAYMENT_DECLINED。409 则不同：payments 的同键操作还持有锁，结果尚未出现；当前 orders 将非 201 的响应标成 FAILED 并释放库存。这个分支是读者必须看到的业务缺口，不能用“Saga 会回滚”一笔带过。

{{fig:order-outcomes.svg}}

先看图的两条状态线：订单状态和扣款状态由不同组件拥有。超时只改变 orders 的知识，不改变支付商正在进行的动作。要消除“已扣款但失败”，可以引入待核对状态，以同一业务键查询支付结果，再决定确认、补单或退款；这会增加状态机和运营流程。仓库有支付结果查询端点，**没有自动对账任务**，本版把它作为设计练习。

## 订单与事件：把双写缩成一次本地提交

确认订单以后，notifier 要知道“可以通知顾客了”。先提交订单再发消息，进程可能在中间崩溃；先发消息再提交，数据库可能回滚。Transactional Outbox 把事件先作为数据保存在 orders 的数据库内。

{{code:order-confirm}}

一个 `c.transaction()` 同时覆盖订单更新和 outbox 插入。事务成功以后，两者都存在；事务回滚，两者都不存在。这里的原子性只到 PostgreSQL 为止，尚未包含 NATS。

{{fig:concept-outbox.svg}}

再沿图看中继：多个 orders 副本各有 relay，行锁与 `SKIP LOCKED` 让它们分摊当前未发布的行。中继发布到 JetStream、收到应答后，再设置 `published_at`。若进程在发布成功后、数据库提交前死亡，下一次会再发布同一事件，所以它提供至少一次投递。

{{code:relay-publish}}

`Nats-Msg-Id` 使用事件 ID，不是本次尝试的新 UUID；否则消息系统无法辨认重复。流配置的去重窗口是 120 秒，窗口不是永久档案。`published_at` 的更新还在外层数据库事务内，锁覆盖等待 NATS 应答的时间；消息系统变慢时，这也会让数据库连接与锁持有更久。

通知端怎样处理重复？

{{code:notifier-dedup}}

消费者先检查 `notifier:done:<event_id>`，已处理就返回 duplicate；否则等待模拟外部工作，再保存 24 小时的已完成标记。随后 `_one()` 才 ACK，异常时 NAK，JetStream 可重新投递。它能避免许多重复，但检查、外部效果、写标记并不是一个原子动作：若发送完成后崩溃而标记未落下，重投仍可能再发送；并发重投也有窗口。真实邮件或支付接口通常还需要接受稳定幂等键，或以可原子提交的消费记录协调副作用。

::: principle
“至少一次 + 去重”要同时说明去重键、保存期限、并发仲裁和副作用窗口。Outbox 解决订单与事件的本地双写，不能自动把任意外部世界变成恰好一次。
:::

## 在真实 Trace 中读出同步与异步

下面是历史一笔成功订单的 Tempo 界面局部。原图保留在仓库；本版只放大能说明调用层次的区域。

{{shot:order-trace}}

按三个问题阅读：第一，父 span 是谁，哪些操作嵌套在 orders 请求内；第二，价格查询是否有重叠，库存与支付是否依次发生；第三，最外层 HTTP 响应结束以后，是否还有异步工作。界面中的 overview 可以看到后段工作，完整记录给出 65 个 span、6 个服务，链路总长约 320.8 ms。

顾客在约 156.6 ms 收到响应，确认事务在约 144.7 ms 提交，中继在约 267.2 ms 开始发布。提交到发布之间约 122.5 ms，主要与中继空闲时每 200 ms 轮询有关；异步通知没有延长 HTTP 响应，却仍有顾客可感知的完成延迟。不能拿整条 trace 的总长替代接口响应时间。[E1](#ev-e1)

追踪能跨消息队列，是因为 orders 把当时上下文保存在 outbox headers，中继以它为父创建 PRODUCER span，再向消息头注入新上下文；notifier 提取它作为 CONSUMER 的父上下文。第 10 章将直接看这个实现，并说明 exemplar 怎样链接到同一条链路。

## Argo CD 管理服务，不能替业务保证正确

平台采用 app-of-apps 与 ApplicationSet：根应用创建平台应用，ApplicationSet 按服务 values 生成六个独立的 Application。同步波次让 CRD、Operator、数据库与服务按依赖出现。

{{fig:concept-app-of-apps.svg}}

E1 首次收敛 735 秒，其中 PostgreSQL 占 437 秒，六个服务本身约 37 秒；副本初始化等待平缓检查点是关键原因。它说明“应用启动慢”可能在它之前的依赖链上。后续重建还暴露波次死锁，第 9 章再分析。

Argo CD 的 Synced 表示被管理清单已符合 Git，Healthy 来自资源的健康判定；它们没有检查扣款与订单账是否一致，也不会证明消息无重复。部署控制与业务不变量应当分别观测。历史基线 20 迭代/秒、5 分钟运行中没有失败，是一组正常条件下的观察；模拟支付、单实例 Valkey、缺少对账和有限去重窗口仍然存在。

## 判断与应用

::: exercise
1. orders 在确认事务提交后、HTTP 响应发出前崩溃。分别说明客户端重试、Outbox 中继、通知副作用会怎样，哪些可能重复，哪些不会凭空丢失。
2. 设计一个支付对账状态机。必须处理超时、409、已成功、明确拒付、查询暂时不存在、补偿再次失败；说明每个动作的稳定幂等键。
3. 当前通知代码能否保证“每个事件只发送一封真实邮件”？给出两条反例时间线，再说明把去重记录放入数据库能消除哪些窗口、仍不能消除哪些窗口。
4. 客户端重放得到 200/PENDING，Argo CD 全部 Healthy。你还需要什么业务信号才能向顾客确认成功？把信号对应到源码中的状态拥有者。
:::

跨服务可靠性从稳定身份开始，经由局部事务与补偿，延伸到可核对的业务终局。平台可以保证对象被部署、请求被路由；业务代码仍必须定义每一种未知结果如何收敛。
