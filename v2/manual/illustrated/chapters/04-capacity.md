# 容量工程：从公式走到性能拐点 {#ch4}

<p class="subtitle">Capacity Engineering · 公式、图像与可证伪的预测</p>

“CPU 平均只有一半，为什么请求已经排队？”因为限制可能在一个单线程进程、一个连接池或一个代理，而不是全节点的平均值。本章把吞吐、CPU 时间、在途请求和尾延迟连起来，再用实测检验一份事先提交的容量预测。

::: mission
能统一单位计算容量，区分模型和实测，找出先饱和的组件，并说明为什么还必须保留失区与发布余量。
:::

## 三个公式，各自回答一个问题

Little's Law 用平均值联系稳定系统中的三个量：$N=XR$。$X$ 是每秒完成量，$R$ 是平均停留秒数，$N$ 是平均在途量。入口、出口和计时范围必须相同；不能把 p95 代入平均响应时间，也不能在队列无限增长的过载阶段不加说明地套用稳态关系。

利用率定律是 $U=XD$，其中 $D$ 为每个请求消耗的资源时间。例如每请求 6 ms CPU，100 请求/秒就消耗 $100\times0.006=0.6$ 核。等待支付 40 ms 不会自动消耗 40 ms CPU，异步程序主要把这段时间让给其他请求。

最简 M/M/1 模型给出 $R=S/(1-U)$。它要求泊松到达、指数服务时间、单服务者等假设。现实中的异步扇出、重试、拒绝与分布不满足这些条件，所以这里用曲线理解接近饱和时等待放大，不用它直接预测所有 p95。

{{fig:model-mm1.svg}}

从左向右读图：$U=0.5$ 时响应为 $2S$，$0.8$ 时 $5S$，$0.95$ 时 $20S$。横轴多出的少量利用率，会在右侧换来很大的等待。工程目标不是让仪表贴着 100%，而是找出业务 SLO 尚有稳定余量的区间。

::: case
**例：用同一窗口算在途请求。**网关每秒完成 64 个请求，平均 26.5 ms，则 $N=64\times0.0265=1.696$。若每 15 秒读一次瞬时在途数，90 秒只得到六七个快照，算出的 0.76 不能推翻定律。

E3 改为密集采样后，网关观测 0.788，而同窗口 $XR=0.747$，相差约 5%。直方图 duration sum 的增长率累加了请求停留时间，比稀疏快照更适合估算平均在途量，但有限窗口边界和未完成请求仍需考虑。
:::

## 一个 Python 进程先满，节点未必满

storefront 每个 Pod 运行一个 Uvicorn 事件循环进程。异步等待允许许多请求共存，CPU 上的 Python 工作却主要由一个线程执行。历史最忙网关约在 0.94–0.96 核附近饱和，给它两核 limit 并不能凭空使单个事件循环并行计算。

真正的容量单位还要分清“迭代”和“HTTP 请求”。负载按 70% 浏览、25% 下单、5% 查订单组织，一次浏览会发多个请求，一次下单还会向下游扇出。模型对服务 $s$ 使用每迭代请求数 $k_s$，CPU 需求 $D_s$，最忙副本份额 $b_s$：

$$C_s=b_s k_s D_s X,\qquad X_{sat}=C_{limit}/(b_s k_s D_s)$$

这里 $D_s$ 必须换算为秒；$X$ 是迭代/秒，$C_s$ 是最忙 Pod 的核数。节点总 CPU 是另一项检查，不能代替这个局部限制。

::: case
**例：预测网关先饱和。**E3 拟合得到 $k=1.61$ 请求/迭代，$D=5.95$ ms/请求，$b\approx0.58$。每迭代最忙副本需求约为 5.5 ms CPU，按 0.95 核上限估算，饱和约在 172 迭代/秒附近。原模型使用未取整参数，不能要求用表中舍入值恰好还原最后一位。

若只留一个副本，$b=1$，总需求约 9.58 ms/迭代，预测约 99 迭代/秒。增加副本能否按比例增加容量，取决于新的 $b$、下游以及节点余量。
:::

## 把预测放在结果前面

E3 预测在提交 `98be3f2` 中先于高负载实验固定。两个副本的运行中，160 迭代/秒最忙网关约 0.801 核，浏览 p95 为 81.4 ms；到 180 时约 0.938 核，p95 跳到 1.18 秒、失败率 13.6%。[E3](#ev-e3)

{{fig:e3-latency-knee.svg}}

这就是从公式走到数据的关键一步：图的拐点支持“网关先饱和”的预测，却没有让其他预测自动全部通过。最忙副本份额从拟合时的 0.58 变成约 0.50–0.53，部分 CPU 档位偏差超出 15%；60 档 p95 以 1 ms 之差超过预设 50 ms 判据。这些偏差保留，不能事后移动阈值让模型全对。

200 档 CPU 反而下降，不是容量变大，而是熔断器打开后快速拒绝大量请求。只看 CPU 会把丢弃业务当成轻松运行。一个容量结论至少要同时看完成吞吐、失败率、尾延迟与负载生成器有没有丢弃迭代。

## 看板上找“谁在等谁”

{{shot:capacity-cpu}}

这张单副本运行的局部中，唯一繁忙网关接近一核，其他服务仍低。紧邻的延迟面板显示网关 p95 跳升。读图时先核对时间与副本，再对比节点总量；不要把某条 0.96 核曲线说成整机 CPU 已满。

在同次单副本实验，catalog 自己处理约 3.3 ms，网关测到的一次 catalog 调用却约 635 ms。差值包括网络、代理和调用方等待，结合网关饱和与事件循环指标，证据指向调用方排队：应答可能已到，协程没有机会继续读它。

{{fig:e3-caller-queue.svg}}

按 $N\approx98\times0.635\approx62$ 个并发调用估算，已经贴近该依赖隔舱 64 的上限，于是大量新调用被拒绝。这个算例把 CPU、在途量与 503 连在一起。不能只因为数据库查询快，就断言请求路径没有排队。

## 优化要说明省下了什么

剖析显示框架、中间件、客户端与插桩占了主要 CPU，业务代码只占少部分。旧 `BaseHTTPMiddleware` 通过额外任务与内存流传递消息；当前源码改用纯 ASGI 中间件，在一个调用链中包裹响应发送。

{{code:asgi-metrics}}

读代码时关注开始计时、捕获状态码、最终更新指标与释放在途量的对应关系。它既是业务请求的观测边界，也是每个请求都要支付的固定成本；因此即使只节省一点，也会在高吞吐时累积。

并排金丝雀对比中，旧 Pod 约 7.26–7.42 ms CPU/请求，新 Pod 约 5.48–5.53 ms，约少 25%；两个旧副本彼此约 2% 差异。这个对比比隔三小时分别跑可靠，但节点、缓存与连接分配仍可能不同。剖析指出位置，受控比较才估计收益。

观测后端也属于容量：Tempo 曾因 1 GiB memory ballast 与较小 GOMEMLIMIT 叠加产生 GC 风暴，空载 CPU 从约 1.34 核修正到 0.027 核。它不是业务算法变慢，却会挤走业务资源。保留平台固定成本，再拟合随流量增长的边际成本，容量预算才完整。

## 从健康容量转向故障容量

按每迭代总需求约 9.2 ms、最忙副本不超过 0.7 核计算，一个副本约承受 76 迭代/秒；两个副本若最忙承担 53%，约 144 迭代/秒。三副本跨三个区时，失去一区后仍剩两个；这些是模型推算，不是三副本生产容量实测。

同时检查内存、数据库连接、代理文件描述符和卷的节点亲和性。E3 的负载均衡器曾因 1024 文件描述符上限反复崩溃，制造“系统全失败但网关 CPU 降低”的假瓶颈。开放模型能揭露过载，但生成器达到 VU 或端口上限时，已发请求也不再代表全部用户需求。

::: warning
模型只适用于被标定的请求组合和状态。缓存失效、热点商品、采样策略、主机降频和重试都会改变每请求需求。历史上尚未解释的升档瞬态、少量客户端超时与 ztunnel 路径停顿，不能从平滑曲线中删除。
:::

## 判断与应用

::: exercise
1. 一个服务 $k=1.6$、$D=6$ ms、最忙副本份额 58%，按 0.95 核算饱和点；改为三个副本、最忙 40% 后再算。解释为什么增益不是恰好 1.5 倍。
2. 180 档失败很多，200 档 CPU 更低。列出三组应联合读取的指标，区分容量恢复、主动拒绝和入口故障。
3. 你必须承诺失去一区后仍能完成 130 迭代/秒。用本章的需求模型给出副本与分布要求，再列出 CPU 模型没有覆盖的验证项。
:::

容量工程的成果是一份可检验的预测及其边界：知道什么先饱和，知道每多一份需求要消耗什么，也知道模型何时已经不再描述当前系统。
