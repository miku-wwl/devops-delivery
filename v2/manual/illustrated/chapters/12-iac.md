# 基础设施即代码：状态、锁与修复 {#ch12}

<p class="subtitle">Infrastructure as Code · 管理工具本身也要可恢复</p>

分支保护被人改松了，OpenTofu 检测到了漂移，apply 也恢复了设置。但计划采用删除重建，main 曾有约一秒完全没有保护。“恢复声明”与“修复过程中持续安全”是两个问题。本章从这次真实行为理解状态、锁、所有权与恢复材料。

::: mission
能说明状态与现实的对应关系，读出计划中的替换风险，设计真实有效的锁测试，并识别 IaC、GitOps 与秘密恢复之间的循环依赖。
:::

## 谁管理哪个对象

Argo CD 持续管理 Kubernetes 中的受跟踪对象，OpenTofu 在执行 plan/apply 时读取和修改基础设施。GitLab 项目设置、分支保护、成员关系不在 Kubernetes 中，本项目由 OpenTofu 接管；Argo CD 自身后来也通过 GitOps 管理。

{{fig:concept-iac-split.svg}}

相同对象需要明确拥有者。若 Helm 与 Argo CD、脚本与 OpenTofu 都把自己当作权威，比较与纠正会互相覆盖。平台与应用分工应落实到具体对象和状态边界，而不是“平台用 Tofu、应用用 Helm”这样的工具口号。

## 接管已有资源：导入不等于重建

{{code:iac-project}}

项目开启“流水线成功才可合并”、拒绝 skipped pipeline，并用 prevent_destroy 限制项目销毁。这个 lifecycle 保护项目资源，不会自动保护另一个分支保护资源的每种替换。阅读计划要逐个资源判断。

E11 导入已有项目、main 保护与 alice 成员共3个资源，第一次计划即3导入、0新增、0修改、0销毁；导入后 GitLab 设置快照一致。一般接管应先让配置贴合现实、确认差异，再把声明作为标准，不能借“纳入 IaC”顺手重建业务资源。[E11](#ev-e11)

## 状态为什么比配置更敏感

状态保存资源地址、远程 ID 与读取的属性，可能包含配置中没有显式写出的 runner 注册令牌。后端权限、传输保护与客户端加密分别保护不同位置。加密也不是可恢复性的替代：失去密钥就无法读状态，持有执行密钥的人仍能接触解密值。

{{code:state-encryption}}

PBKDF2 从仓库外口令派生键，AES-GCM 处理状态与计划，enforced 拒绝未加密写入。这段真实配置解释加密边界，口令不出现在教材。密钥备份、轮换与恢复必须另行设计，不能从这几行推断已经验证。

原工程使用 GitLab root 令牌，管理范围又只有一个项目；生产流水线应按实际操作权限设计专用身份、状态分区、计划产物访问和 apply 审批。当前仓库没有完整实现定时漂移 CI，本章不会把建议画成已运行流水线。

## 锁需要原子仲裁，S3 兼容不代表全部语义兼容

{{fig:concept-state-lock.svg}}

沿图看两个执行者：它们都可能读到相同状态，只有原子加锁才让第二个停住。普通“先读不存在、再写锁”仍有竞争窗口。S3 lockfile 依赖条件写；GitLab HTTP state 使用专门 lock 接口。

历史 Garage v2.5.0 忽略 If-None-Match，同键第二次条件写仍200，Tofu 没有被别人的锁挡住，退出后还删了那个锁。换到 GitLab state 后，第二次加锁409，并发 plan 一个成功一个被拒。这是实际后端行为验证，不能只通过配置中出现 use_lockfile 就宣布有锁。

{{shot:state-lock}}

这幅是仓库保存的**终端记录排版局部**，不是 GitLab 网页。局部A显示409，局部B显示plan拒绝与锁持有信息；完整原图还保留解除后的成功。没有保留网页素材，本版不制造 State 页面。

状态迁移曾被主机注销打断。恢复前先核对后端地址、资源数量、serial/lineage、锁与工作目录指向，再运行只读计划；不能因中断就重复导入或强行解锁。GitLab state 与被管理 GitLab 同系统，还留下管理平面共故障风险。

## 计划以2退出，下一步不应自动apply

`plan -detailed-exitcode` 的0是无差异、1是错误、2是有变化。CI 若把2当普通失败，会漏掉“成功检测到漂移”的语义；若见2就自动apply，又可能移除安全控制。

{{shot:drift-plan}}

历史三处注入改动中，成员关系就地更新，但 push_access_level 要替换分支保护。`must be replaced` 对应先删后建，main 约一秒无保护。计划摘要1 add、1 change、1 destroy不是三件独立业务需求，而含同一对象的替换。

判断应包括：替换期间哪个不变量消失，有没有并行保护，提供者是否支持就地修改，是否需要临时限制发布身份、低风险窗口或先做覆盖保护。自动检测值得做，自动修复需要按资源语义决定。本书不把那次一秒窗口删掉，也不声称已实现持续漂移治理。

## Argo CD 自管理：引导与日常变更分开

第一次安装仍需 bootstrap，随后一个 Application 指向同一 Chart 与 values。接管先比较差异、不自动同步；确认后再开启，避免把跟踪注解变化误认为数十个实质对象变化。

E11 初看59个资源56个OutOfSync，服务器端试运行只有1个实质对象不同，其余主要是跟踪信息。接管后没有Pod重启；随后Chart从10.14.0升级到10.17.1，经MR门禁后315秒恢复Synced/Healthy，应用版本仍为Argo CD v3.6.1。它是一次Chart变化实验，不能证明跨大版本、CRD迁移也安全。

{{fig:e11-argocd-upgrade.svg}}

流程外 Helm 4 修改先被 server-side apply 字段所有权拒绝；强制覆盖后又被 selfHeal 拉回。字段冲突是所有权保护信号，不是看到报错就应加 force。Helm 历史也可能从此不再描述真实状态，因此退路要明确读取哪个权威版本。

## 事故：快照还在，解封密钥却被清空

E11-1 重启后，脚本把“OpenBao没应答”误判为“尚未初始化”。Shell 输出重定向先截断唯一 init.json，然后命令失败；已有的快照仍在，却再也打不开。四个条件组合致命：过期 Pod 状态、吞掉错误的探测、直接覆盖文件、密钥无独立副本。

修复后等待 OpenBao 自己应答，区分未初始化与不可达；已有材料时拒绝重新初始化，新材料写临时文件再移入，并只读保存第二份。旧密文按 Retain 留存，恢复由当时所有者明确批准。出版工作没有执行清卷、初始化或恢复。

一个原因还生成54个事故，说明告警抑制必须理解依赖；第13章用合成告警验证规则。本轮能核实的密钥副本仍不能证明虚拟机之外已经完成可恢复验证，应继续标为接受风险而非PASS。

## 云迁移先迁移边界，再选择服务

不要直接把Kind节点替换成云VM就宣布灾备完成。应先明确备份在哪个账号与区域、删除权限是否与生产分离、解密材料由谁保管、管理GitLab故障时如何取回状态。不可变存储也要配合版本、保留策略和实际恢复测试，锁与加密分别验证。

本版保留原云迁移分析的固定历史链接，不把它在2026-11-10核对的服务支持状态当成当前承诺，也不追加价格或新云资源。这里可迁移的教学结论是恢复依赖不能构成循环，具体托管服务选择需要部署时再次查官方文档。
