# 服务网格：连接、请求与重试的边界 {#ch3}

<p class="subtitle">Istio Ambient · 把真实流量路径画出来</p>

两个 inventory 副本已经就绪，为什么其中一个承担了 97% 的请求？再加上透明加密，是否就能自动均衡？答案取决于代理究竟在连接层还是请求层作决定。本章以长连接为线索，把加密、身份、waypoint 和重试叠加放在同一张流量地图里。

::: mission
能够画出无网格、Ambient L4 与 Ambient L7 的请求路径，预测扩容后旧连接会去哪里，并用两层计数识别隐形重试。
:::

## 一次 TCP 选择，会影响后面许多 HTTP 请求

kube-proxy 在连接建立时把 Service 流量送往某个后端。HTTP 客户端为了避免反复握手会保留连接；连接不换，后端也不换。两条连接面对两个副本，假设独立均匀选择，则两条都落到同一副本的概率是 $2(1/2)^2=50\%$。请求数量很大并不能弥补连接数量很少。

{{fig:concept-l4-l7.svg}}

图的左边按连接选择，右边按请求选择。L7 代理终止客户端连接、解析 HTTP，再为每次请求选择后端，同时维护自己的后端连接池。它改变的是选择发生的时机。保持连接的收益仍然存在，只是连接两端由代理重新组织。

E2 从服务端连接表核对出两个 orders 各只有一条到 inventory 的长连接，两条都落在同一个副本。客户端 Pod 只看到 ClusterIP，并不知道节点上 DNAT 后的地址；所以判断失衡要同时看连接与服务端每 Pod 请求数。[E2](#ev-e2)

## Ambient 把安全层与七层处理拆开

无网格时应用直接以明文 HTTP 通信。Ambient L4 引入节点级 ztunnel，CNI 把工作负载流量重定向给它；它处理身份、mTLS 与 L4 策略，不解析 HTTP。Ambient L7 再引入 waypoint，为需要 HTTP 能力的目标服务处理请求级路由、授权和指标。

{{fig:concept-ambient-path.svg}}

从发送方开始沿图读：应用并没有自己建立 mTLS；ztunnel 根据工作负载身份管理安全隧道。HBONE 使用 mTLS 上的 HTTP/2 CONNECT，网络上看到的是到 15008 端口的隧道。需要 waypoint 的路径多一段代理处理，不能把它理解为每个 Pod 中多了一个 sidecar。官方数据面说明见附录 E 的 R2。

SPIFFE 身份关联命名空间与 ServiceAccount，例如 orders 的身份包含 `ns/storefront/sa/orders`。IP 会随 Pod 重建变化，身份则服务于“谁可以调用谁”的策略。独立 ServiceAccount 因而不只是部署清单中的命名习惯。

E2 抓包在同一节点 eth0、10 秒窗口内观察到服务间可读请求行从 140 变成 0；外部负载均衡器送来的 `/api/...` 仍有明文。它验证的是选定跨节点路径上的加密，不能扩大为“所有入口、出口与存储都已加密”。STRICT mTLS 还会切断网格外合法调用方；启用前必须盘点入口与 Prometheus 等客户端。

先按 legend 确认每条线对应 Pod，再比较同一时间窗口内的面积与形状，最后核对模式切换时刻。图中约 08:03 后的两条新副本曲线接近；更早的 L4 阶段一条高、另一条接近零。Pod 更新会换颜色，不能一直把“绿色”当作固定实例。

三种模式下，inventory 无网格是 97.1%/2.9%，只有 ztunnel 是 97.2%/2.8%，经过 waypoint 后是 49.7%/50.3%。这不是说 L4 永远得到同一比例，而是说明加密没有改变连接复用的机制；换一轮连接，可能换另一个副本“中签”。五个同步服务在 L7 下的副本份额均落在 46.9%–53.1%。[E2](#ev-e2)

## 代理开销：先排除时间漂移

两次相隔 15 分钟的运行，订单 p50 相差 32.4 ms。但主机状态、模拟支付抽样和后台活动也改变了。交替 A/B 运行后，浏览 p50 在三轮中增加 2.1–2.7 ms，平均约 2.4 ms；订单差值却跨过零，在该实验精度下无法确定。再比较 L4 与 L7，waypoint 对浏览 p50 的增量约为 1.3 ms。

{{fig:e2-ab.svg}}

图的价值在于比较各轮差值是否稳定。若只看平均数，很容易给漂移贴上“网格成本”的标签。低负载的一跳成本不等于高负载吞吐上限；共享宿主机的绝对数值也不能拿去预算生产集群。L7 增加代理、连接池、CPU 与故障点，收益是按请求控制与统一观测，取舍应基于所需能力。

## 重试为什么会躲过应用预算

orders 的应用客户端给每个逻辑调用存入预算，只为自己发出的尝试计数。如果 waypoint 把这一次尝试再重试三次，应用只知道一次调用，下游却收到四次。

{{fig:e2-retry-stack.svg}}

E2 的 S3 中，应用发出 7 次 payments 尝试，服务端收到 28 次。21 次额外调用没有消耗应用的 RetryBudget。这里真正需要比较的是“客户端尝试计数”和“服务端接收计数”，不能只看重试配置是否各自合理。故障恢复期间还要考虑熔断器状态是否从上一场景延续。

本次 Istio 1.31.4 的源码及实验记录没有观察到默认对 503 的状态码重试；显式 HTTPRoute 配置才产生上述四倍。不要把一次版本的默认值概括为所有网格的永久保证。业务级重试适合放在知道操作是否幂等的调用方；连接级重试、代理重试和应用尝试总量仍要共同计入容量。

## 回到那笔“已扣款、订单失败”

{{shot:ambiguous-trace}}

在原始 Tempo 局部中，先找带错误的调用，再看关键路径所指向的 `POST /charges`，最后对照客户端超时与服务端最终结果。历史链路中 payments 有约 917 ms 的停顿，orders 的 1 秒尝试超时，重试遇到同键锁返回 409，于是补偿并标记 FAILED；扣款后来保存为 approved。这个停顿也出现于无网格轮次，原因至今未找到，不能归咎于网格。

第 2 章的源码使这张截图有了业务含义：保护连接、避免重复扣款和释放库存分别完成自己的工作，组合后仍需要对账。网格无法替应用决定“未知是否等于失败”。本章没有新增对账实现，也没有重现停顿。

## 判断与应用

::: exercise
1. 三个副本、三条独立均匀长连接，至少一个副本没有连接的概率是多少？若这三条连接每秒共发出一万次请求，概率是否改变？
2. 应用每个逻辑调用最多额外发 20% 尝试，waypoint 每次最多三次重试。为什么不能直接承诺下游仅增加 20% 负载？需要在哪两端核对？
3. 准备启用 STRICT，但 Prometheus 与外部入口都在网格外。给出迁移顺序与验证条件，明确区分身份、网络端口和 HTTP 业务成功。
:::

网格改变网络路径，业务库定义操作语义。能够把一条请求穿过哪些代理、在哪一层选择后端、每一层重试多少画清楚，才有条件解释延迟与故障。
