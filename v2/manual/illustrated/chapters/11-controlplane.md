# 控制面规模：一万个对象为什么能压垮 API {#ch11}

<p class="subtitle">Control Plane at Scale · 缓存、版本、队列与资源代价</p>

一个客户端循环列出全部 Pod，大多数请求已经被 APF 拒绝，API Server 仍因内存耗尽重启。限制请求并发并没有限制每个请求的成本。本章把 API、watch 缓存与 etcd 的工作拆开，解释虚拟规模实验能够证明的机制和不能证明的生产容量。

::: mission
能跟踪一次 LIST 的数据路径，区分调度限速与算法瓶颈、etcd 有效空间与文件大小，并解释 APF 席位为何不等于内存配额。
:::

## KWOK 没有启动一万个业务容器

KWOK 控制器代替 kubelet 写节点心跳与 Pod 状态，kwokctl 则启动真实 etcd、API Server、scheduler 和 controller-manager。一个 Pod 被绑定到虚拟节点后，状态可以被写成 Running，却没有拉镜像、启动容器、配置真实网络或挂载卷。

{{fig:concept-kwok-env.svg}}

实验包含 1000 个 `[虚拟]` 节点和 10000 个 `[虚拟]` Pod。图中把真实控制面与虚拟对象分开，目的在于限制结论：可以观察对象存储、调度绑定、LIST 与 WATCH 的处理，不能据此证明这台电脑能运行一万个工作负载，更不能验证生产节点侧的心跳与状态更新总成本。

这套控制面与业务集群仍共用 WSL 内存。第一次洪水未加硬上限，冻结了整个虚拟机；后续才给各组件加 cgroup 上限。本轮出版没有再次启动 KWOK。

## 调度完成之前，还有谁在写 API

scheduler 筛选与打分后，要向 API Server 写 binding。客户端令牌桶限制这个写入速率。默认 QPS50、burst100 时，即使算法很快，持续绑定也约每秒 50 个。

{{fig:e10-scheduling.svg}}

E10 默认配置中全部调度约 193 秒，创建结束后的斜率约 50.3 个/秒。放开客户端限速后，29.4 秒全部调度，48.6 秒全部 Running；此时创建一万个对象已经花 27.5 秒，测到的是创建端限制和 KWOK 状态写入，不是调度算法真正上限。[E10](#ev-e10)

若由一个 Deployment 扩到一万副本，先创建 Pod 的是 ReplicaSet 控制器，它还有自己的 QPS。只调整 scheduler 不一定改善创建队列。调高一个客户端的上限，会把更多写入、事件和 watch 更新转给共享 API 与 etcd；“消除限速”本身不是免费的优化。

## etcd 删除对象，为什么文件先变大

etcd 的 MVCC 保存修订历史。更新和删除都会产生新版本，优雅删除还可能先写删除标记。Compaction 清理旧 revision 使页可复用；defragmentation 重写有效页才可能缩小文件。两项工作的目标不同。

{{fig:concept-etcd-space.svg}}

E10 删除一万个最小 Pod，文件从 92.5 增至 172.7 MiB；压缩后有效数据降下去，文件仍不缩，碎片整理后才约 18.7 MiB。因为删除也要写入，接近配额时大批删对象可能先触发 NOSPACE，而不是立即腾出空间。

{{fig:e10-etcd.svg}}

通过每次物理压缩和整理，实验测得最小 Pod 的边际有效空间约 3.73 KiB。真实 Pod 可能带多个容器、探针、卷与 managedFields，不能用这个常数乘生产对象数就给出最终配置。

::: case
**例：先估静态有效数据，再估历史与突发。**若自己的对象实测每 Pod 12 KiB，40000 个约占 $40000\times12/1024\approx468.75$ MiB，再加其他对象 300 MiB，共约 768.75 MiB。

这不是 etcd 文件最大值。还要加修订历史、批量更新/删除、事件、碎片与预留。生产多成员碎片整理会影响成员服务，应按官方维护流程逐个操作；本轮不运行任何维护。
:::

## LIST 与 WATCH：重复快照比持续增量贵

控制器通常先 LIST 获得当前状态，再 WATCH 获取变化。API Server 为资源维护 watch cache，并通过 etcd watch 更新。缓存减少 etcd 读，不消除序列化、编码、传输和客户端解析成本。

{{fig:concept-list-paths.svg}}

本次 Kubernetes v1.37 的一致 LIST 也由缓存提供：API 先取得要求的 revision，等待缓存追上，再回答。`resourceVersion=0` 允许使用缓存已有视图；分页和带不同条件的读取还需按版本与请求语义判断，不能说所有参数组合永久同路。

E10 一万个 Pod 完整 JSON 约 33 MiB、0.88–1.23 秒，对照 etcd 实际请求计数没有增加 Pod LIST。某个存储层 list 指标却会连缓存回答也计入，第一次归因因此错误。指标名字包含 storage 不等于每次访问了 etcd。

分页遍历曾花 5.6–7.1 秒，脚本却在每页启动新 Python 进程解析 JSON。总耗时包含客户端工作，不能据此说服务器分页慢六倍。控制器改为 informer、缩小选择器范围和正确续 watch，通常比每十秒全量 LIST 更符合这个数据模型。

## APF：分类、席位、队列与借用

FlowSchema 先按身份、动词与资源分类；PriorityLevel 为一类请求分配席位；繁忙流排队，队列满时返回 429。`nominalConcurrencyShares` 决定名义份额，不是独占硬资源；未限制借用时还能借空闲席位。

{{fig:concept-apf.svg}}

E10 低优先级名义 3 席位，只设 lendablePercent=0 代表不借出，不能阻止它借入。显式 borrowingLimitPercent=0 后观察到 3 执行、5 排队，分类与拒绝均按配置工作。该次大 LIST 每个只计 1 席位，与预想按对象数量加权不同，原因未查明；不能把它宣称为所有 Kubernetes LIST 的固定行为。

{{fig:e10-apiserver-memory.svg}}

即使只有三条大 LIST 在执行，API Server 相比静态状态仍多用约 1.4 GiB；1536 MiB 上限下反复被杀，2560 MiB 上限下仍被杀一次。33 MiB 是响应字节，不是处理它只需 33 MiB 内存。对象集合、编码、缓冲、并发与 GC 余量共同增加工作集。

APF 没有为每个优先级建立独立堆或 CPU。另一个优先级的 GET 未被拒绝，也可能因共享 CPU 与 GC 变慢。七次配置没有一次使受害者 p99 保持在安静时两倍以内；这是被推翻的保护假设，而不是 APF 不分类的证据。

## API 重启后的错误码来自不同层

重启探测看到连接失败、403、429，再到 200。403 出现在 RBAC 状态尚未加载的启动窗口，429 也可能来自 storage/watch cache 初始化，不全是 APF 队列拒绝。仅汇总状态码会混淆原因。

生产应让入口只把流量转给 ready 的 API 实例；客户端仍需要对可重试故障退避，不能无间隔空转。多实例控制面提供实例级容错，但同配置、同缓存重建和共用 etcd 仍有相关压力，不能把多副本当作无限保护。

真正减少成本还要回客户端：一次快照加增量，选择器、分页、限速、断线续订与抖动退避。硬内存上限把整机冻结缩小成单个进程重启，是重要的隔离改进，但没有修复无效的全量读取模式。

## 判断与应用

::: exercise
1. ReplicaSet 创建速率上限20/秒，scheduler 绑定上限50/秒，忽略其他开销时，一万个 Pod 的完成下界由谁决定？创建提高到200/秒后呢？
2. 低优先级只有3席位，受害者 GET 仍变慢。解释至少三个共享资源路径，并指出 APF、cgroup 和客户端改造各能控制什么。
3. 用 KWOK 验证3万对象的 LIST 方案时，哪些结果可用于解释控制面机制，哪些仍要在真实节点与工作负载中测量？
:::

控制面容量是对象、请求模式、版本历史与客户端行为共同的结果。把限制移走以前，要先知道它把压力挡在了哪一层。
