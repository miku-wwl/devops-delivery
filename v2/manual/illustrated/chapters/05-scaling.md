# 弹性与调度：多一个副本，为什么仍然慢 {#ch5}

<p class="subtitle">Autoscaling & Scheduling · 控制回路、流量与资源竞争</p>

HPA 已经从两个副本扩到四个，用户却仍有五分之一请求失败。先不要把目标利用率继续调低：扩出的 Pod 可能根本没有收到请求。本章把扩容的判断、执行、调度与流量生效拆开，再看 CPU 和内存竞争为何采用不同规则。

::: mission
能从负载时间线定位扩容慢在哪一步，分清 Requests 的三种用途，预测节点压力下的驱逐，并为队列消费者设计稳定副本目标。
:::

## HPA 控制的是副本目标，不是用户延迟

HPA 定期读取指标、计算目标、修改 scale 子资源。简化公式为：

$$n_{desired}=\left\lceil n_{current}\frac{m_{current}}{m_{target}}\right\rceil$$

CPU utilization 的分母是 requests，不是 limit。请求 500m、实际用 0.5 核，利用率才是 100%；若仍请求 50m，同样工作就显示 1000%。请求值同时影响调度装箱、CPU 争用权重和 HPA 百分比，三个用途不能分开随意填数。

{{fig:concept-hpa-loop.svg}}

沿控制回路读图：指标采集先延迟，HPA 计算再延迟，Deployment 创建 Pod，调度器找到位置，容器启动、探针通过，路由最后接纳新端点。Missing metrics、未就绪 Pod、容差、稳定窗口和扩缩策略还会修正简化公式。官方算法细节见附录 E 的 R1。

::: case
**例：算出4，控制器就一定扩到4吗？**以下为教学算例：当前3个副本，每个CPU request为500m，目标100%，采用10%容差。

1. **先找分母。**平均用650m时，利用率为 $650/500=130\%$，指标比值为1.3；分母是request，不是节点总核数。
2. **再算整数目标。**$\lceil3\times1.3\rceil=4$。比值已在容差外；缺失指标、上下限与扩容策略仍可能修正结果。
3. **用反例检查。**若平均只用540m，比值为1.08，向上取整也会得到4；但它仍在10%容差内，控制器保持3。数学取整不能跳过控制规则。

即使期望已变成4，还要分别检查Pod就绪与实际分流；这两个状态由回路中的其他环节决定。
:::

E4 使用约 15 秒指标与控制周期、10% 容差和 300 秒缩容稳定窗口。120 迭代/秒台阶中，利用率在 102%–114% 边缘摆动，326 秒后才扩容；决定以后只花 8 秒就绪。因此“Pod 启动快”与“扩容响应快”是两件事。目标应在性能拐点以下，为测量、决策与启动时间留下空间。[E4](#ev-e4)

## 谁拥有 replicas 字段

Git 中固定 `replicas: 2`，Argo CD 自愈就会把 HPA 的修改拉回。当前 Chart 用条件省略字段，让动态扩缩容接管。

## 扩出来，不等于分到流量

{{shot:hpa-replicas}}

先在副本面板看期望数与就绪数是否跟上，再转到同一窗口的每 Pod CPU。若旧 Pod 接近一核，新 Pod 接近空载，平均值会掩盖过载。E4 的两个新网关在高负载阶段请求数都为 0，原来的两个各约 140 请求/秒；四个平均约 0.43 核，看起来正好满足目标。[E4](#ev-e4)

{{fig:e4-new-pods.svg}}

原因与第 3 章相同：入口按 TCP 连接分配，k6 的长连接在扩容前已经固定到旧副本。加新端点没有搬走旧连接上的请求。L7 入口可以按请求重新选择；客户端限制连接寿命也能增加重新选择机会，但会增加握手和端口成本。E4 强制频繁建连的对照还耗尽了负载机端口，不能用那次失败来否定扩容。

第 9 章确实验证了 L7 入口让新 Pod 分担，却仍没有让 170 迭代/秒台阶成功。弹性由整条链最窄的地方决定，不能把流量分配修复等同于容量已经充足。

## KEDA：队列长度与到达速率是两种信号

通知服务模拟每条 200 ms、并发 2，单副本能力约为 $2/0.2=10$ 条/秒。CPU 低不代表跟得上，积压才显示工作没有完成。只按积压扩容又会产生另一个问题：一旦积压清空，公式认为一个副本够了，稳定窗口结束后缩回，随后再次积压。

{{fig:e4-keda-oscillation.svg}}

E4 恒定流量中出现以约 300 秒为周期的缩至 1、再扩容，缩容后通知 p95 约 20 秒。当前 values 增加订单确认速率触发器：一笔确认产生一条通知，按每副本 8 条/秒、即约 80% 利用率决定稳态。

{{code:keda-rate}}

这里的 Prometheus 查询测量到达速率，NATS 触发器测量未处理积压，取要求副本最多的指标。若稳定到达 22–23 条/秒，$\lceil23/8\rceil=3$；若短时积压很大，积压触发器仍能要求更多。历史修改后稳定在 3 个，常态 p95 0.48–0.73 秒。它没有消除从低副本起步的最初积压，需要更高最小副本或提前扩容才能覆盖。

## CPU 的请求给份额，限制给暂停

CPU requests 在争用时成为 cgroup 权重；空闲时仍可多用。E4 权重实测约为 50m→2、500m→20、2 核→79。BestEffort 批处理只用剩余 CPU，对网关影响很小；同一个消耗者声明 2 核后，同节点网关 p50 从约 16 ms 变成 131 ms。它按声明取得更多竞争份额，未必违反任何限制。

{{fig:e4-neighbor.svg}}

CPU limit 则变成周期配额。300m 在本实验对应 100 ms 周期最多运行 30 ms；平均只用 0.282 核，仍有 67% 周期被限流，事件循环 p99 从约 6 ms 变为 95.5 ms。平均值无法描述周期内突发。延迟敏感服务应根据隔离需求、可信程度与成本决定是否设置 CPU limit，并同时看 throttled periods 与延迟；不能把“不设 CPU limit”推广成多租户中无条件的规则。

## 内存压力：QoS 不是简单的驱逐队列

内存不能像 CPU 那样暂停一会儿就归还。kubelet 根据工作集压力驱逐 Pod，排序关注是否超过 requests、优先级和超出量。优先级相同，一个 Burstable 请求 64 MiB、使用 776 MiB，超出 712；BestEffort 使用 160、请求 0，超出 160。历史上前者先走。

{{fig:concept-eviction-order.svg}}

驱逐前，内核已经回收同节点数据库页缓存，从 411 降到 115 MiB；RSS 相对稳定。没有被驱逐不等于没受影响。E4 内存增长仅每秒 3–4 MiB，超调不到 10 MiB；若一瞬分配数百 MiB，可能来不及等 kubelet 统计更新，先碰到 cgroup OOM。这种快增长情况没有在原实验验证。

调度抢占是另一机制：高优先级 Pending Pod 找不到位置时，调度器选择较低优先级牺牲者。批处理若设为正优先级，可能让默认优先级 0 的在线业务先被抢占；实验采用负优先级且 Never。PDB 不能防止全部非自愿故障，也不会为不存在的资源创造空间。

## 放得下，还要放在正确故障域

`ScheduleAnyway` 是软分布建议，`DoNotSchedule` 宁可 Pending 也保持约束。节点不可用时还要明确它是否参与拓扑计数；排除故障域可以优先保证副本总数，但允许副本集中到剩余区。节点回来后，调度器不会主动迁移已经运行的 Pod。

LimitRange 与 ResourceQuota 是准入边界。配额可能接受 Deployment 却拒绝它后续创建的 Pod，所以要看 ReplicaSet 事件。E4 还发现仅写 `max.cpu` 会补出默认 CPU limit，团队可能在不知情时被限流。检查渲染前清单还不够，要看准入之后的有效 Pod。
