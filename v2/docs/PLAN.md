# 第二轮：企业级生产环境高保真仿真（v2）

> 制定：2026-11-07 ｜ 基线：`v1.0.0`（`b062e78`）｜ 分支：`v2/enterprise` ｜ 状态：[STATUS](STATUS.md)

## 1. 目标与边界

在一台笔记本（31 GB 内存，WSL2 分得 15.6 GiB，16 线程）上，用真实软件搭建尽可能接近企业生产的多服务平台，围绕 Senior DevOps / Platform Engineer / SRE 的核心能力做可验证的实验：架构与服务间通信、负载与容量、弹性与调度、多租户与安全、故障与恢复、数据可靠性与灾难恢复、发布治理、可观测性与 SLO、大规模控制面、IaC 与云迁移。

**三条硬性规则：**

1. **标注真实性。** 所有实验与图表标注其性质：
   - `[真实]` 真实运行的进程、真实的请求与数据；
   - `[虚拟]` KWOK 模拟的节点与 Pod（只有控制面是真实的，没有容器在运行）；
   - `[注入]` 人为注入的故障（Chaos Mesh、故障开关）；
   - `[模拟]` 用实验手段代替的企业设施，例如“可用区”只是同一台电脑上不同 Kind 节点的标签，“外部支付服务”是我们自己写的模拟器。
2. **不夸大。** 结论只覆盖实际测到的范围；单机实验的数字不外推为生产容量；能力验证不等于生产经验，文档中不虚构生产规模或工作经历。
3. **零付费。** 只用本地开源软件和 GitHub 免费额度；不创建任何云资源。云迁移只做分析。

## 2. 环境设计

| 组件 | 选择 | 理由 |
|---|---|---|
| 集群 | 新的 Kind 集群 `ent`：1 个控制面 + 3 个工作节点，节点标签 `topology.kubernetes.io/zone=zone-a/b/c`（`[模拟]` 可用区） | 与 v1 的 `lab` 隔离；三个“可用区”用于拓扑分布、分区故障实验 |
| v1 集群 | 第二轮实验期间 `docker stop` 暂停，随时可 `docker start` 恢复 | 内存预算；v1 状态完整保留 |
| Git 与 CI | 复用本地 GitLab（第二轮的配置仓库 `root/platform-gitops`）与 GitHub Actions | 合并请求流程与策略检查可以完整运行 |
| 服务网格 | Istio ambient 模式（ztunnel + waypoint）+ Gateway API | 企业最常见的网格；ambient 没有 sidecar，内存开销小；L7 流量按请求分配，解决 v1 金丝雀按连接分流的问题 |
| 数据 | CloudNativePG（PostgreSQL 高可用、WAL 归档、PITR）、Valkey、NATS JetStream | 关系数据、缓存、异步消息三类典型依赖 |
| 对象存储 | S3 兼容存储，放在集群外（Docker 容器），作为“异地”备份目标 | 集群整体损毁时备份仍在 |
| 弹性 | metrics-server、HPA、KEDA | CPU 与自定义指标（队列积压、请求速率）伸缩 |
| 故障注入 | Chaos Mesh | 网络延迟、丢包、分区、Pod 故障、压力 |
| 备份 | Velero（文件系统备份）+ CNPG 备份 | 集群资源与数据卷、数据库两条线 |
| 大规模 | KWOK（独立的控制面集群） | 只验证控制面，节点与 Pod 为 `[虚拟]` |
| IaC | OpenTofu（状态存放在 S3 兼容存储，带锁） | 开源、与 Terraform 语法兼容 |

工具版本在 E0 固定到 `v2/platform/versions.env`，下载的二进制校验 SHA256，镜像尽量按 digest 引用。

## 3. 被交付的系统：storefront

一个刻意设计成“小而完整”的多服务系统（`v2/apps/`），所有服务由本项目编写，便于精确注入故障和观察传播：

```text
           ┌──────────┐  HTTP   ┌──────────┐  HTTP   ┌───────────┐  HTTP  ┌────────────────────┐
 k6 ─────► │ gateway  │ ──────► │ orders   │ ──────► │ inventory │        │ payments-sim        │
           └──────────┘         └──────────┘ ──────► └───────────┘        │ （[模拟] 外部支付）  │
                │ HTTP               │  │  └─────────────────────────────► └────────────────────┘
                ▼                    │  │ SQL（CNPG）        事件（NATS JetStream）
           ┌──────────┐              │  └────────────────► ┌───────────┐
           │ catalog  │ ─ Valkey 缓存 └─ outbox 表 ─────────► │ notifier  │（异步消费者）
           └──────────┘                                     └───────────┘
```

韧性机制按需开关，用来做对照实验：超时、带抖动的重试与重试预算、熔断、舱壁（连接池上限）、幂等键、事务性 outbox。

## 4. 阶段与验收标准

| 阶段 | 主题 | 关键实验（全部 `[真实]` 运行，另有标注者除外） | 验收标准 |
|---|---|---|---|
| E0 | 平台基线与资源预算 | 建 `ent` 集群；kubelet 预留与驱逐阈值；测量各层的真实资源占用；资源预算表 | 集群可重复创建；预算表来自实测 |
| E1 | 多服务系统 | storefront 六个服务 + CNPG + Valkey + NATS；GitOps（app-of-apps）部署；跨服务（含异步消息）的链路追踪 | 一笔订单的完整链路（同步 + 异步）在 Tempo 中可见；单元测试与集成测试通过 |
| E2 | 服务网格与 L7 流量 | Istio ambient：mTLS 验证、L7 负载均衡对比 L4（复用 v1 的长连接实验）、超时与重试策略 | 有网格时长连接上的请求均匀分布；mTLS 有抓包或指标证据 |
| E3 | 负载与容量规划 | k6 阶梯加压找拐点；Little 定律；连接池饱和；容量模型（CPU 限流移至 E4，与资源请求和限制一起） | 每个服务的“吞吐—延迟”曲线与容量模型，预测值经一次实测验证 |
| E4 | 弹性与调度 | HPA（CPU）与 KEDA（队列积压）扩缩的时间线；CPU 限流（`cpu.stat`，从 E3 移入）；优先级与抢占；配额；拓扑分布（E3 中 catalog 的两个副本落在同两个节点上）；节点压力驱逐；吵闹邻居 | 扩容延迟、驱逐顺序、抢占结果都有实测时间线 |
| E5 | 多租户与安全治理 | 租户命名空间；RBAC 权限矩阵测试；NetworkPolicy 默认拒绝；Kyverno 策略；Argo CD 项目隔离；API 审计日志；外部密钥管理 | 越权操作被拒绝的测试矩阵全部符合预期；审计日志能回答“谁做了什么” |
| E6 | 故障注入与传播 | `[注入]` 依赖变慢 → 重试风暴与级联失败，加上超时/熔断/舱壁后的对照；Pod 与节点故障；可用区分区；GameDay 与复盘 | 每个实验都有假设、稳态指标、结果与 SLO 影响 |
| E7 | 数据可靠性与灾难恢复 | 被卷固定的组件（PostgreSQL、NATS、Tempo、Loki、OpenBao）使用 PriorityClass platform-critical（E6 事故二）；PostgreSQL 主库故障切换（测 RTO 与丢失的写入）；WAL 归档与时间点恢复；Velero 备份恢复；整个集群损毁后的重建 | 实测 RTO/RPO；误删数据被时间点恢复找回 |
| E8 | 发布治理 | ApplicationSet；入口 L7 路由（网关 API），重做 E4 的 HPA 台阶，验证扩出的副本能分到请求；Argo CD 按项目的同步冒用（E5：项目边界目前只由 Argo CD 执行）；网格加权金丝雀与按请求头的预览；配置仓库合并请求的策略检查；变更冻结窗口；部署事件与 DORA 指标自动统计；同步波次在空集群上的验证与并行化（E7：两次重建暴露两处波次死锁，修复后重建仍需 15.3 分钟，波次 -3 占 4.6 分钟） | 违反策略的配置变更在合并前被拒绝；精确到 5% 的金丝雀 |
| E9 | 可观测性与事故响应 | 节点级日志采集（E4 中被驱逐 Pod 的标准输出没有被收集）；审计策略补记服务账号读取 Secret（E5）；由 SLO 规格生成规则；尾部采样；exemplar；告警路由与抑制；事故响应演练；监控不与被监控者同一故障域（E7 F4：唯一的 Prometheus 与主库一起被冻结，告警在故障切换结束后才触发）、OpenBao 密封告警、Velero 备份警告告警（`velero_backup_warning_total`）；AlertmanagerClusterCrashlooping 在 E7 期间一直触发（Alertmanager 未重启，原因未查）；Argo CD 同步失败告警（E8：冒用开启后根应用 7 分钟无法同步，无人察觉） | 演练的检测、升级、缓解时间线完整，复盘有行动项 |
| E10 | 大规模控制面 | `[虚拟]` KWOK 节点与 Pod：调度吞吐、API 延迟、etcd 体量、APF 限流 | 测量结果与规模边界写清楚，虚拟与真实严格区分 |
| E11 | IaC 与云迁移 | OpenTofu 管理平台组件，远程状态与锁，漂移检测；AWS/Azure 迁移分析，包括不可删除的异地备份（E7：备份与集群在同一台机器上，Garage 没有对象锁）；Argo CD 自身的升级纳入合并请求（E8：唯一一次故障来自流程外的 helm upgrade） | `tofu plan` 能发现手工漂移；迁移分析只陈述可核实的事实 |
| E12 | 能力考核与教材 | 架构设计题、故障排查题（脚本注入故障 + 自动判分）、独立实操考核；第二册 PDF 与验收报告 | 考核脚本可运行；PDF 经逐页检查与证据核验 |

## 5. 资源与清理

- 每个阶段开始前记录可用内存，结束时记录峰值；超过预算的组件按阶段启停（例如 Chaos Mesh、Velero、KWOK 只在对应阶段运行）。
- 每个实验都有清理脚本或清理步骤；`[注入]` 的故障必须有明确的结束条件。
- 每完成一个阶段提交一次 Git 检查点，并更新 [STATUS](STATUS.md)。

## 6. 能力与经验的边界

本轮验证的是“在受控环境中，能否正确地设计、实施、测量和排查”。它不能替代生产经验：真实生产有更大的规模、真实用户、跨团队协作、合规审计与长期运行带来的问题。文档中所有数字都来自这台电脑上的实验。
